# KMH 模型请求停止与状态监督

用户在会话中发起的每次模型请求都能看到当前阶段、耗时和重试情况；点击"停止"后立即看到"正在停止"，并在数秒内得到"本机任务已停止"或"停止状态待确认"的明确结果；停止后排在后面的消息与自动续跑被挂起，点"继续"才恢复；晚到的模型回复不会被当作新指令执行；每次请求的证据可查、页面刷新不丢失。依据与实际交付范围见 [请求监督说明](../../research/zcode-cli-request-supervision.md)。

## 当前交付范围

本规格定义验收目标。当前原生中继以 `session/stop` 回执确认 CLI 回合停止；进程范围清空、请求证据持久化、诊断导出和宿主重启恢复分别按任务清单验收。后续目标与当前实现差异由[请求监督说明](../../research/zcode-cli-request-supervision.md)集中维护；历史 task-stop-chain 报告对应旧裸模型协议。

## feat01: 查看模型请求的阶段与进度

用户在会话内实时看到当前模型通信进行到哪一步。

场景1: 正常请求
- GIVEN 用户在会话中发出一条消息
- WHEN 模型通信进行中
- THEN 请求状态区依次显示"启动模型通道""等待模型回复"，并显示已等待时长

场景2: 自动重试
- GIVEN 模型服务中断后自动开始第二次尝试
- WHEN 重试进行中
- THEN 显示"第 2 次尝试"，第一次尝试的失败原因可在详情查看

场景3: 慢请求提示
- GIVEN 模型回复等待超过 30 秒（可配置）
- WHEN 等待继续
- THEN 显示慢请求提示，请求不中断

场景4: 内部阶段未知
- GIVEN 某个中间阶段无法从实际回复得知
- WHEN 请求继续
- THEN 显示"等待模型回复"，不虚构阶段

## feat02: 停止当前模型请求

用户点击一次"停止"即可终止本轮模型请求，并得到本机已停止的明确确认。

场景1: 正常停止
- GIVEN 一条模型请求正在等待回复
- WHEN 用户点击"停止"
- THEN 按钮立即变为"正在停止"（不等任何回复），通常数秒内变为"本机任务已停止"

场景2: 停止与完成同时发生
- GIVEN 用户点击"停止"时模型回复恰好已经生成完毕
- WHEN 停止请求送达
- THEN 显示"取消时请求已完成"，该回复按晚到结果处理（见场景4），不视为停止失败

场景3: 停止确认超时
- GIVEN 停止后数秒内无法确认本机已完全回收
- WHEN 确认时限到达
- THEN 显示"停止状态待确认"，会话保持挂起；详情展示已发生的证据与日志入口

场景4: 晚到的模型回复
- GIVEN 停止已生效
- WHEN 模型的文本或工具调用请求才送达
- THEN 其中任何操作都不被执行，处置记录保存在该请求的详情中

场景5: 两个会话并行
- GIVEN 两个会话的模型请求同时运行
- WHEN 用户只停止其中一个
- THEN 仅该会话的请求被停止，另一会话正常完成

## feat03: 停止后挂起排队消息与自动续跑

停止操作同时挂起该会话排队的消息与自动续跑入口，用户显式选择后才恢复。

场景1: 挂起排队内容
- GIVEN 用户在请求运行中追加过待发送消息
- WHEN 用户点击"停止"
- THEN 待发送队列与自动续跑入口显示为已挂起，不会自动继续

场景2: 显式继续
- GIVEN 会话处于挂起状态
- WHEN 用户点击"继续"
- THEN 挂起的排队消息与续跑按记录顺序恢复执行

场景3: 补充本轮
- GIVEN 会话处于挂起状态
- WHEN 用户选择"补充本轮"并输入内容
- THEN 新内容进入下一步处理，不恢复已挂起的队列

场景4: 挂起期间保存输入
- GIVEN 会话挂起且存在待处理输入
- WHEN 用户关闭后重新打开该会话
- THEN 排队内容仍然可见，可继续、编辑或删除

## feat04: 区分终止原因

每个请求的结束原因被如实归类并展示，先发生的原因不被后续事件覆盖。

场景1: 首个原因保持
- GIVEN 请求因总时限到期被停止，随后清理又出错
- WHEN 用户查看请求结果
- THEN 终止原因显示"模型请求总超时"，清理错误作为独立信息一并展示

场景2: 原因类别
- GIVEN 任一请求结束
- WHEN 用户查看结果
- THEN 至少区分：用户停止、启动超时、模型请求总超时、提供方错误、模型通道提前退出、宿主卸载、清理失败

场景3: 超时如实归类
- GIVEN 请求因总时限到期被停止
- WHEN 用户查看结果
- THEN 显示"模型请求总超时"而非"用户取消"

## feat05: 查看请求详情与证据

用户可查看每个请求的完整证据链，并导出脱敏诊断。

场景1: 展开详情
- GIVEN 任一模型请求存在
- WHEN 用户展开该请求的详情
- THEN 展示阶段时间线、各步耗时、重试记录、结束原因、停止操作记录（接收时间、取消回执、本机回收确认）与日志文件入口

场景2: 页面刷新
- GIVEN 一个请求正在进行或待确认
- WHEN 用户刷新页面
- THEN 该请求状态从记录重建，不丢失

场景3: 导出诊断
- WHEN 用户导出诊断
- THEN 得到本地文件，其中密钥、令牌与鉴权信息已脱敏

## feat06: 会话暂停的一致性

同一会话内的后台调度、目标续跑与子代理投递遵循同一暂停状态。

场景1: 后台任务挂起
- GIVEN 会话有计划任务或自动续跑
- WHEN 该会话被停止并挂起
- THEN 这些后台工作同样挂起，不产生新的执行

场景2: 子代理挂起
- GIVEN 会话挂起时有子代理待投递
- WHEN 挂起持续
- THEN 子代理投递同样挂起，待处理输入保存

## feat07: 重启后的停止状态恢复

宿主异常退出后，未确认的停止状态在重启时保持可见并可恢复。

场景1: 重启后保持待确认
- GIVEN 宿主退出时有停止尚未确认的请求
- WHEN 用户重启后打开该会话
- THEN 该请求显示"停止状态待确认"，会话保持挂起

场景2: 恢复检查完成
- GIVEN 会话存在待确认请求
- WHEN 恢复检查完成
- THEN 状态落定为"本机任务已停止"或明确的未知说明，会话恢复可用

## feat08: 模型通信最小初始化

每次模型请求的通信过程只加载必要组件，多余组件加载时用户能看到失败原因。

场景1: 最小加载
- GIVEN 模型请求正常发起
- WHEN 通信过程初始化
- THEN 额外的插件数、外部工具服务数与钩子数为零，请求正常进行

场景2: 检测到多余组件
- GIVEN 通信初始化加载了插件、外部工具服务或钩子
- WHEN 兼容检查完成
- THEN 该请求拒绝启动并显示"初始化包含多余组件"的原因

场景3: 版本不支持最小模式
- GIVEN 当前模型通道版本无法关闭全部多余组件
- WHEN 用户发起请求
- THEN 显示该版本最小运行模式不可用的原因，请求不静默降级
