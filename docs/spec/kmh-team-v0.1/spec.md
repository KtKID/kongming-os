# kmh-team 团队会话第一版

用户可以保存固定 Agent 角色，并用这些角色创建团队会话。KMH 主 Agent 自动作为每个团队的 owner 加入，用户为它选择模型，并选择额外成员。普通消息由 owner 回应，用户点名其他成员时，该成员才收到本次消息与最近的群聊内容并开始回应。成员在其余时间保持静默。群聊在成员完成后展示完整回复，实际执行任务期间在对应头像下显示“工作中”。成员的工具和 skill 继承本团队 owner。本文状态为方案确认；实现约束见[实现约束](constraints.md)。

## feat01: 创建并保存可复用的 Agent 角色

用户可以通过配置或让主 Agent 创建角色，保存后将同一角色加入多个团队。

场景1: 通过配置创建角色
- GIVEN 用户准备创建一位固定角色
- WHEN 用户填写角色名称和职责说明并保存
- THEN 角色出现在可选列表中，用户可以查看已保存的名称和职责，并将其加入团队作为额外成员

场景2: 让主 Agent 创建角色
- GIVEN 用户正在与主 Agent 对话
- WHEN 用户要求“创建一位写手，负责撰写和修改博客文章”
- THEN 主 Agent 创建并保存该角色，向用户报告保存结果，角色出现在团队配置的可选列表中，用户可以通过配置弹窗选择加入团队

场景3: 同一角色用于不同团队
- GIVEN “程序员”角色已经保存，用户已有团队 A 和团队 B
- WHEN 用户分别把“程序员”加入两个团队并在各自群中点名
- THEN 两个团队显示相同的角色名称与职责，该角色分别围绕各自群聊中本次提供的内容回应

场景4: 必填内容为空
- GIVEN 用户正在创建角色
- WHEN 用户提交空白名称或空白职责说明
- THEN 页面指出需要补充的内容，保留已填写的配置供用户修改

场景5: 保存失败
- GIVEN 用户填写了完整角色配置
- WHEN 保存过程中发生错误
- THEN 用户看到保存失败的说明与重试入口，已填写内容继续保留，创建结果标记为待保存

场景6: 重启后使用已保存角色
- GIVEN 角色已经成功保存
- WHEN 用户重启 KMH 并打开团队配置
- THEN 可选列表仍显示该角色及其已保存的职责

## feat02: 从新建会话入口配置团队

用户在“新建会话”下方打开“团队会话”，主 Agent 自动作为 owner 加入，弹窗提供 owner 的模型选择和额外成员选择。

场景1: 打开团队配置弹窗
- GIVEN kmh-team 已启用，用户正在查看会话列表
- WHEN 用户点击“新建会话”下方的“团队会话”
- THEN 弹出团队配置窗口，上方固定显示作为 owner 的主 Agent 和初始为默认模型的模型选项，下方显示额外成员的已加入列表与可选列表，以及“取消”和“确认”按钮

场景2: 加入或移除成员
- GIVEN 弹窗中有已加入成员和可选角色
- WHEN 用户点击可选角色加入，再点击已加入角色移除
- THEN 两侧列表随操作更新，同一额外角色在已加入列表中出现一次，主 Agent 始终固定显示在 owner 区域

场景3: 选择主 Agent 的模型
- GIVEN 弹窗中主 Agent 已自动作为 owner 加入，且有可用模型
- WHEN 用户在 owner 区域将默认模型改为另一个可用模型
- THEN owner 身份保持为主 Agent，弹窗显示所选模型，确认创建后 owner 使用所选模型回应普通消息

场景4: 确认创建团队
- GIVEN 主 Agent 已自动作为 owner 加入，用户已选定可用模型和若干额外成员
- WHEN 用户点击“确认”
- THEN 会话列表新增该团队并打开群聊，群聊显示 owner 和已选成员，成员处于待命状态

场景5: 取消创建
- GIVEN 用户已经在弹窗中调整了成员选择
- WHEN 用户点击“取消”或关闭弹窗
- THEN 返回原会话，原会话和已保存角色保持原状，本次选择作为已取消处理

场景6: 仅由主 Agent 接待
- GIVEN 主 Agent 已自动作为 owner 加入，模型可用，额外成员列表为空
- WHEN 用户点击“确认”
- THEN 创建由 owner 接待的团队会话，用户可以向 owner 发送普通消息

场景7: 创建条件缺失或创建失败
- GIVEN 主 Agent 当前不可用、所选模型已不可用，或保存团队时发生错误
- WHEN 用户点击“确认”
- THEN 弹窗显示具体原因，保留选择供用户修正或重试，成功创建后才打开团队会话

场景8: 重复点击确认
- GIVEN 一次团队创建正在处理中
- WHEN 用户连续点击“确认”
- THEN 这次创建完成后，会话列表只新增一个团队

场景9: 主 Agent 与额外成员分别展示
- GIVEN 用户打开团队配置弹窗
- WHEN 用户查看两侧成员列表并点击额外角色加入或移除
- THEN 两侧列表仅包含额外角色，主 Agent 固定保留在上方 owner 区域，该区域提供模型选择

## feat03: 默认与 owner 对话，其他成员保持待命

用户发送普通消息时由 owner 接待，固定成员的收件与回应由用户提交的有效点名触发。

场景1: 发送普通消息
- GIVEN 团队已经创建，owner 可用
- WHEN 用户发送一条普通消息
- THEN 群聊显示用户消息和 owner 回复，其余成员保持待命

场景2: 群聊持续产生新内容
- GIVEN 用户与 owner 连续交谈，群中还有“程序员”和“写手”
- WHEN 用户与 owner 产生多条新消息
- THEN 回复者持续为 owner，“程序员”和“写手”的收件与回应次数保持原值

场景3: 曾经回应过的成员回到待命
- GIVEN “程序员”已经完成一次被点名的回应
- WHEN 用户随后继续向 owner 发送普通消息
- THEN owner 回应后续消息，“程序员”保持待命，收件与回应次数保持原值

场景4: owner 暂时无法回应
- GIVEN owner 当前无法使用所选模型
- WHEN 用户发送普通消息
- THEN 群聊显示 owner 无法回应的说明和重试入口，其余成员继续待命

场景5: owner 的正文提及其他成员
- GIVEN owner 正在回答普通消息
- WHEN owner 在回复正文中写出其他成员的名称或点名文字
- THEN 群聊显示这段正文，其他成员保持待命；下一次成员回应由用户提交的有效点名触发

场景6: 根据成员的公开回复向 owner 追问
- GIVEN “程序员”已经在群中提交回复并回到待命
- WHEN 用户向 owner 发送针对该回复的普通追问
- THEN owner 结合群中的公开回复回答，“程序员”继续待命

## feat04: 点名成员并让它在群中回应

用户通过本团队的成员候选名单点名，只有被选中的收件人开始回应。

场景1: 首次点名一位成员
- GIVEN “程序员”已加入团队并保持待命
- WHEN 用户在输入框选择“程序员”作为点名对象，输入任务并发送
- THEN 群聊显示这条消息，“程序员”使用本团队 owner 的所选模型和自己的角色职责处理本次要求并以自己的身份回复，owner 和其余成员继续待命

场景2: 再次点名同一成员
- GIVEN “程序员”先前已经回应过，当前保持待命
- WHEN 用户再次点名“程序员”并提出新要求
- THEN “程序员”按本次提供的最近群聊内容回应，先前保存在其他成员对话中的内容保持各自归属

场景3: 点名候选范围
- GIVEN 团队成员为 owner、“程序员”和“写手”，其他已保存角色属于可选角色库
- WHEN 用户在群聊输入框打开点名候选名单
- THEN 候选名单显示本团队的 owner 和成员，用户可以明确选中收件人

场景4: 点名多位成员或重复点名
- GIVEN “程序员”和“写手”均属于本团队
- WHEN 用户在同一条消息中点名两位成员，并重复点名“写手”
- THEN 两位成员各收到一次相同的本次群聊内容，各自回应；回复按完成顺序显示，重复点名合并为一次收件

场景5: 仅点名 owner
- GIVEN 用户在候选名单中选中了 owner
- WHEN 用户提交任务
- THEN owner 回应本次消息，其余成员保持待命

场景6: 引用文本或代码中的点名文字
- GIVEN 用户的正文、引用或代码片段包含“@程序员”，且用户尚未选择有效点名对象
- WHEN 用户发送这段内容
- THEN 这段文字作为普通消息交给 owner 处理，群中其他成员保持待命

场景7: 目标不可用
- GIVEN 用户选中的成员当前无法启动或无法使用所需能力
- WHEN 用户发送点名消息
- THEN 群聊显示该成员无法回应的说明，用户可以重新点名重试，其他未点名成员保持待命

场景8: 点名目标或任务内容失效
- GIVEN 点名对象已经失效，或用户只填写了点名而任务内容为空
- WHEN 用户尝试发送
- THEN 输入区指出需要重新选择成员或补充任务，保留草稿供用户修改

## feat05: 控制点名时传递的最近对话数量

用户在 kmh-team 插件详情页配置传递数量，默认使用最近 20 条群聊可见消息。

场景1: 使用默认的 20 条
- GIVEN 群聊已有 24 条可见的用户消息和回复，传递数量为默认的 20
- WHEN 用户点名一位成员并提交第 25 条消息
- THEN 该成员收到按群聊显示顺序排列的第 6 至第 25 条可见消息，计数包含本次用户消息，每条保留发言者信息

场景2: 当前群聊少于配置数量
- GIVEN 当前群聊在本次发送后共有 6 条可见消息，配置数量为 20
- WHEN 用户点名成员
- THEN 该成员收到这 6 条消息，并围绕本次要求回应

场景3: 更改数量
- GIVEN 用户打开 kmh-team 插件详情页
- WHEN 用户将“传递上下文数量”改为 5 并成功保存，再点名成员
- THEN 详情页显示已保存的 5，后续点名使用最近 5 条可见消息，重启后该设置继续保留

场景4: 配置数量为 1
- GIVEN 传递数量已保存为 1
- WHEN 用户点名成员并发送任务
- THEN 该成员收到本次用户消息并回应，其他群聊内容作为较早记录保留

场景5: 输入无效或保存失败
- GIVEN 用户正在修改传递数量
- WHEN 用户填写空值、零、负数、小数或其他文字，或保存过程中发生错误
- THEN 页面指出问题，继续采用上次成功保存的值，并保留有效草稿供用户修改或重试

场景6: 回应期间修改数量或出现新消息
- GIVEN 用户已提交点名消息，成员正在处理当时选定的最近对话
- WHEN 用户修改传递数量，或群中出现后续消息
- THEN 本次回应继续使用提交时选定的内容，之后提交的点名使用新数量和新的最近对话

场景7: 群聊之外的内容与工作记录
- GIVEN 用户与同一角色在另一个团队或私聊中有对话，当前团队中还有执行工作记录
- WHEN 用户在当前团队点名该角色
- THEN 本次传递的群聊内容仅取自当前团队的用户消息与 Agent 回复，其他团队、私聊及执行工作记录保持各自归属

场景8: 选定内容超过成员可处理范围
- GIVEN 最近对话中包含较长的消息，完整内容超过当前成员可处理的范围
- WHEN 用户提交点名任务
- THEN 群聊说明内容过长并提示精简内容或调小传递数量，该次回应标记为失败，用户可以调整后重试

## feat06: 查看完整回复和头像下的工作标记

成员完成后，群聊显示署名的完整回复。owner 或成员实际执行任务期间，其头像下显示“工作中”；工作标记分别反映当前团队中每位回应者的实际执行情况，执行过程与详细工作记录保存在各自记录中。

场景1: 成员完成回应
- GIVEN 被点名的“写手”完成了当前唯一执行的任务
- WHEN 系统取得完整回复
- THEN 群聊追加一条署名为“写手”的完整回复正文，保留其中的格式和可访问的成果链接，该成员本次任务结束后清除“工作中”标记

场景2: 成员执行多步工作
- GIVEN 被点名成员正在查询、检查或修改内容
- WHEN 成员执行多步工作并产生工作记录
- THEN 该成员头像下持续显示“工作中”，回复完成后显示完整正文，执行步骤、调用详情与详细运行状态保留在成员自己的工作记录中

场景3: 多位成员结束时间不同
- GIVEN 同一条用户消息点名了多位成员
- WHEN 成员分别完成本次回应
- THEN 每条回复使用实际回应者的名称并按完成顺序显示，同一份完成回复出现一次；当前团队中全部任务已结束的成员清除工作标记，仍有任务执行的成员继续显示“工作中”

场景4: 回应失败或回复为空
- GIVEN 被点名成员当前唯一执行的任务以失败结束，或结束时缺少可展示的正文
- WHEN 系统展示本次结果
- THEN 群聊显示该成员本次回应失败的简明说明，已结束任务的“工作中”标记清除，用户可以重新点名重试，其余收件人的结果继续分别显示

场景5: 重新打开已有回复
- GIVEN 成员回复已成功保存到群聊，该成员在当前团队的任务均已结束
- WHEN 用户切换会话后返回，或重启后重新打开团队
- THEN 群聊仍显示原发言者署名和原回复正文，每条已保存回复显示一次，已结束任务的头像恢复普通显示

场景6: 任务实际开始后显示工作标记
- GIVEN 用户已提交普通消息或成员点名，回应者尚在等待任务开始
- WHEN 对应 owner 或成员实际开始处理该任务
- THEN 对应头像下显示“工作中”；开始前头像保持普通显示，其他待命成员保持普通显示

场景7: 同一任务进入下一步工作
- GIVEN owner 或成员正在处理包含多步工作的任务
- WHEN 一项检查结束，回应者继续分析、执行下一步或整理最终回复
- THEN 该回应者的头像下持续显示“工作中”，当前团队中该回应者的全部实际执行任务结束后清除标记

场景8: 较早任务的结束通知延迟到达
- GIVEN 某成员已经结束较早的任务，并开始处理新的任务
- WHEN 较早任务的结束通知晚到或重复到达
- THEN 新任务的头像下继续显示“工作中”，较早任务的回复仍对应原任务并显示一次

场景9: 同一成员仍有其他任务执行
- GIVEN 同一团队中的某成员有多项任务正在执行
- WHEN 其中一项任务结束
- THEN 该成员头像下继续显示“工作中”，所有实际执行的任务结束后再清除标记

场景10: 同一固定角色在不同团队中的工作状态
- GIVEN 固定角色“程序员”在团队 A 中执行任务，在团队 B 中保持待命
- WHEN 用户切换到团队 B
- THEN 团队 B 中“程序员”的头像保持普通显示，返回团队 A 时显示该团队中实际仍在执行任务的“工作中”标记

场景11: 切换会话或刷新后恢复实际工作状态
- GIVEN 当前团队中部分回应者正在执行任务，部分回应者的任务已经结束
- WHEN 用户切换会话后返回，或在 KMH 持续运行期间刷新页面
- THEN 正在执行任务的回应者头像下显示“工作中”，已结束任务的头像保持普通显示，每个标记对应各自当前团队的实际任务

场景12: 等待停止确认
- GIVEN 某回应者仍在执行当前唯一的任务，用户已点击停止
- WHEN 系统请求停止并等待实际结束
- THEN 执行期间头像下继续显示“工作中”，确认任务结束后清除标记，已结束任务的重复通知保持头像普通显示

## feat07: 使用 owner 的工具和 skill 能力处理点名任务

第一版成员使用本团队 owner 的工具和 skill 能力，并沿用 owner 已有的操作范围。

场景1: 使用 owner 已有的工具能力
- GIVEN owner 具备检查当前项目文件的能力
- WHEN 用户点名“程序员”检查同一项目
- THEN “程序员”使用 owner 的相应能力完成检查，并在群聊中报告结果

场景2: 使用 owner 已有的 skill
- GIVEN owner 已配置适用于写作任务的 skill
- WHEN 用户点名“写手”并要求按该 skill 处理文章
- THEN “写手”使用这项 skill 处理任务，并以自己的身份提交正文

场景3: 所需能力超出当前操作范围
- GIVEN owner 当前的操作范围不足以完成某项工作
- WHEN 用户点名成员执行该工作
- THEN 该成员遵循同样的操作范围，向用户说明完成任务所需的条件，已有成果继续保留

场景4: 工具或 skill 暂时不可用
- GIVEN owner 配置的某项能力在本次使用时发生错误
- WHEN 被点名成员尝试使用该能力
- THEN 群聊显示该成员的失败或部分完成说明，用户可以根据提示调整要求后重新点名

## feat08: 停止回应并恢复已保存的团队会话

用户可以停止正在处理的回应，并在刷新或重启后查看保存的团队配置和群聊记录。

场景1: 停止当前回应
- GIVEN owner 或被点名成员正在处理当前要求
- WHEN 用户点击团队会话的停止按钮
- THEN 当前团队中正在处理的回应接受停止请求，执行期间对应头像继续显示“工作中”，确认结束后清除标记并显示简明停止说明，团队与既有完整回复继续保留

场景2: 停止后重新点名
- GIVEN 上一次成员回应已经停止
- WHEN 用户重新点名该成员并提交要求
- THEN 该成员按这次选定的最近对话开始新的回应

场景3: 恢复已保存团队
- GIVEN 团队和群聊记录已经成功保存
- WHEN 用户刷新页面、切换会话后返回，或重启 KMH 后打开团队
- THEN 页面恢复作为 owner 的主 Agent、创建时选定的模型、成员和完整群聊记录，工作标记按实际仍在执行的任务恢复，其余成员继续待命

场景4: 回应期间发生重启
- GIVEN 一次回应尚未完成时 KMH 重启
- WHEN 用户重新打开该团队
- THEN 群聊显示这次回应已中断的简明说明，原任务的“工作中”标记清除，完整的已有消息继续可见，用户可以重新发送普通消息或点名来发起新的回应

场景5: 停止或恢复失败
- GIVEN 停止状态仍在确认，或某个团队的保存记录读取失败
- WHEN 用户查看该团队
- THEN 页面给出停止仍待确认或读取失败的简明说明，并保留可读取的已有记录；实际仍在执行的任务保留“工作中”，读取失败可通过重试恢复

场景6: 回应已经结束
- GIVEN 当前团队的所有回应均已完成或停止
- WHEN 用户再次执行停止操作
- THEN 页面显示当前已经结束的状态，既有完整回复和团队配置保持原状
