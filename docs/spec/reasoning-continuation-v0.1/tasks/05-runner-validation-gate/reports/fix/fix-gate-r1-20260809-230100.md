## 问题与根因

| # | 严重度 | 处置 | 说明 | 反例/验证 |
|---|---|---|---|---|
| issue-1 | P1 | ✅ 已修 | Runner 原先仅按 `LLMRequest.reasoning_effort` 判断门禁；OpenAI/Anthropic provider 会在该字段为空时采用 `ResolvedModelConfig.default_reasoning_effort`。两处真源出现不同值时，含 tool call 的缺失 state 响应会越过 assistant append、approval 与 tool execute 前的校验。 | `tests/unit/test_runner_reasoning_projection.py::test_provider_default_reasoning_effort_keeps_pre_side_effect_gate` |

## 修复内容

- `SupportsReasoningContinuationGate` 将 provider 解析后的实际 reasoning 状态公开为 core 合同。
- `BaseLLMProvider` 统一解析 request effort 与模型默认 effort，并以同一 `resolve_reasoning_plan()` 结果提供 gate；OpenAI 与 Anthropic payload encoder 复用这个有效 effort。
- Runner 优先使用该 provider gate，保留未知 provider 的 request-level fallback。
