# 移动端管家与任务委派第一版

用户通过移动端与 KMH 管家沟通。管家使用独立配置的在线模型，负责理解需求、安排执行、跟进状态和汇报结果。全部任务交给 Codex 或 ZCode 执行者完成；用户指定执行者时，管家遵循该选择。用户用日常语言提出需求，系统提供已配置好的委派能力。

## feat01: 由固定管家接待和安排任务

用户始终与管家沟通，实际任务由执行者处理。

场景1: 提交需要实际处理的任务
- GIVEN 管家和至少一个执行者可用
- WHEN 用户要求查询资料、分析问题、修改文件或验证结果
- THEN 管家将工作交给 Codex 或 ZCode，接收执行者报告后向用户汇报

场景2: 日常沟通与需求澄清
- GIVEN 用户与管家建立对话
- WHEN 用户问候、说明偏好或提出信息不足的需求
- THEN 管家直接回应或澄清需求，具备执行条件后安排执行者

场景3: 管家对话能力不可用
- GIVEN 管家当前无法连接自己的在线模型
- WHEN 用户提交需求
- THEN 用户看到管家暂时不可用的说明和重试提示，任务保持待处理

## feat02: 用自然语言触发已配置的委派能力

用户描述目标即可安排任务，委派所需的启动格式由系统维护。

场景1: 按日常表达交付任务
- GIVEN 系统已配置任务委派能力
- WHEN 用户说“检查这个项目的测试，并告诉我失败原因”
- THEN 管家通过已配置的委派能力安排执行，并说明任务目标与执行者

场景2: 任务包含特殊文本
- GIVEN 用户的任务包含多行文本、引号、中文路径或代码片段
- WHEN 用户提交任务
- THEN 执行者收到完整的任务内容，文本原意和内容保持一致

场景3: 任务内容为空
- GIVEN 用户尚未提供实际任务内容
- WHEN 用户提交空白消息或仅指定执行者
- THEN 管家提示用户补充任务目标

场景4: 委派能力不可用
- GIVEN 系统尚未配置可用的任务委派能力
- WHEN 用户提交任务
- THEN 管家说明需要补齐执行能力配置，任务保持待处理

## feat03: 由用户指定或由管家选择执行者

每次任务明确交给 Codex 或 ZCode；用户指定的选择具有最高优先级。

场景1: 用户指定 Codex
- GIVEN Codex 可用
- WHEN 用户说“用 Codex 完成这个任务”
- THEN 管家将该任务交给 Codex，并向用户说明所选执行者

场景2: 用户指定 ZCode
- GIVEN ZCode 可用
- WHEN 用户说“这个任务交给 ZCode”
- THEN 管家将该任务交给 ZCode，管家继续使用自己的对话能力

场景3: 用户交给管家决定
- GIVEN 用户已给出任务目标
- WHEN 用户将执行者选择交给管家
- THEN 管家从可用的 Codex 和 ZCode 中选择一个，并说明选择结果

场景4: 指定的执行者不可用
- GIVEN 用户已指定 Codex 或 ZCode，所选执行者启动失败或当前不可用
- WHEN 管家安排该任务
- THEN 管家反馈所选执行者的失败状态，询问用户选择重试或更换执行者

场景5: 同一任务的选择存在歧义
- GIVEN 同一条任务消息包含相互冲突的执行者要求
- WHEN 管家准备安排任务
- THEN 管家请求用户明确选择，任务保持待处理

## feat04: 由管家接收执行报告并交付结果

执行者独立处理任务，管家接收其最终报告并整理交付。

场景1: 任务成功完成
- GIVEN 执行者已完成任务并提交报告
- WHEN 管家收到报告
- THEN 用户看到管家整理的完成说明、交付物位置和已有的验证结果

场景2: 执行者开展多步工作
- GIVEN 执行者正在检查、修改或验证任务
- WHEN 执行者产生中间说明和工作记录
- THEN 主对话显示管家提供的任务状态，执行过程保留在执行者自己的记录中

场景3: 任务部分完成
- GIVEN 执行者完成了部分工作，剩余工作遇到限制
- WHEN 管家收到报告
- THEN 用户看到已完成内容、剩余内容和限制原因，任务状态标记为部分完成

场景4: 报告缺失或任务失败
- GIVEN 执行者退出时任务失败或缺少可用的交付报告
- WHEN 管家收集执行结果
- THEN 用户看到失败或结果待确认的状态，以及可以采取的下一步

## feat05: 根据已有成果安排后续任务

用户可以追问、补充要求或为后续工作更换执行者，管家负责交接已有成果。

场景1: 沿用原执行者处理追问
- GIVEN 原任务已经结束，管家持有执行报告和交付物位置
- WHEN 用户提出针对该成果的追加要求
- THEN 管家优先安排原执行者，并提供原任务目标、已有成果和追加要求

场景2: 指定另一执行者处理后续工作
- GIVEN 原任务已经结束，已有成果可以作为后续工作的依据
- WHEN 用户要求“接下来交给 ZCode”或“接下来用 Codex”
- THEN 管家将后续任务交给用户选择的执行者，并提供已有成果和剩余工作说明

场景3: 交接信息不足
- GIVEN 管家缺少原任务报告或交付物位置
- WHEN 用户要求继续原任务
- THEN 管家说明缺失的信息，并向用户确认后续目标或安排执行者重新检查

场景4: 原任务执行期间提出更换要求
- GIVEN 原执行者仍在处理任务
- WHEN 用户要求更换执行者
- THEN 管家先停止原任务，确认停止状态后收集已有成果并安排新的执行者

## feat06: 停止任务与如实反馈等待状态

用户可以停止正在执行的任务，并获知停止、超时和异常退出的结果。

场景1: 用户停止任务
- GIVEN 执行者正在处理任务
- WHEN 用户要求停止
- THEN 管家请求执行者停止，确认结束后报告停止结果和已知的已有成果

场景2: 任务长时间无法结束
- GIVEN 执行者超过系统配置的等待时间
- WHEN 系统处理等待超时
- THEN 管家报告任务超时，并说明停止结果或仍在确认的状态

场景3: 停止状态尚待确认
- GIVEN 管家已请求停止，执行者的结束状态仍待确认
- WHEN 用户查询任务状态
- THEN 管家显示“正在确认停止状态”，并在结束状态确定后更新说明

场景4: 任务已经结束
- GIVEN 任务已完成、失败或停止
- WHEN 用户再次要求停止
- THEN 管家说明任务当前的最终状态，已有交付物继续可供查看

## 待确认默认

- feat01 场景2：问候、偏好说明与需求澄清由管家直接处理，需要实际查询或操作的工作统一委派。
- feat05 场景1、2：追加要求作为新的委派任务，管家附上已有成果和追加目标。
- feat05 场景4：执行期间更换执行者，先确认原任务停止，再交接已有成果并启动后续任务。
