kongming-agent v1 Minimal

这页按 docs/kongming-agent-v1-minimal 当前口径重画 v1-mini 架构图。 它表达的是一个宿主无关、单 agent、单 run loop 的最小闭环：先用 CLI 跑通， 再在同一组边界上扩展后续宿主与工程能力。

主轴：单 agent / 单 run loop / 单宿主验证路径 SSOT：共享协议只定义在 core/contracts.py 装配：native_runtime.py 执行：core/runner.py 安全顺序：capability → permission → approval → execute 观测：单个 JsonlTraceSink

边界规则

1. 协议真源

跨模块共享协议只定义在 core/contracts.py。

core 决定语言，其他模块提供实现。

2. 装配与执行分离

native_runtime.py 负责装，core/runner.py 负责跑。

CLI 负责进，不复制装配逻辑。

3. 安全顺序固定

capability -> permission -> approval -> execute。

Tool Runtime 只消费装配后的高层判定结果。

4. 事件模式固定

runner 持有 list[EventSink]，统一 fan-out。

v1 当前唯一 sink 是 JsonlTraceSink。

11 步主流程

这组步骤严格按 v1-mini 文件布局文档组织，每一步都落到具体文件职责。

1
cli/main.py 启动进程，解析参数和配置，进入 cli/repl.py。
CLI 是第一个真实宿主入口。
2
cli/repl.py 负责交互壳，读取用户输入，准备把本轮请求送入宿主桥接层。
3
host/cli_adapter.py 把终端输入输出和审批交互翻译成统一宿主接口。
4
host/session_bridge.py 把宿主输入翻译成 agent 运行请求，并在 run 结束后把结果回写给宿主。
5
executors/agent_runtime/native_runtime.py 装配 session、provider、tool registry、event sink 和高层安全链。
它负责装配，不负责第二套 loop。
6
core/runner.py 启动唯一 run loop，推进 turn，维护 RunState，并驱动整个执行过程。
7
context/session_store.py、history_compactor.py、instruction_loader.py、 input_assembler.py 负责准备模型输入。
顺序是 session history -> instruction loading -> history compaction -> input assembly。
8
executors/llm/openai_responses.py 发起模型调用，把 provider 返回结果转换回统一消息协议。
9
如果模型发出 tool call，tools/registry.py 按工具名分发到具体实现。
10
tool 执行前固定经过 capability -> permission -> approval，然后才进入具体 tool execute。
默认 approval 实现在 tools/approval.py，安全链由装配层串接。
11
core/runner.py 把事件 fan-out 给 EventSink 列表，当前唯一实现是 observability/trace_sink.py；最终结果由 core/result.py 收口，再回到 host / cli 输出给用户。

横切能力说明

Context

这一层负责“模型看到什么”。它不定义 Session 协议，它消费既有 Session 语义，补工程化存储、规则加载、历史压缩和输入组装。

Tools

这一层负责“模型能调用什么”。它提供最小 tool 总线、builtin tools 和默认 approval 实现，让模型可以发起调用并拿回结果。

Observability

这一层负责“系统发生了什么”。v1 只保留单个 JSONL trace sink，usage 和 audit 留给 v0.2+ 从同一事件流派生。

Safety

这一层负责“能力怎样被放行”。v1 先收住 capability、permission、approval 三段链路，把工具调用边界固定清楚。
