# KMH 插件式基础框架

为 Kongming Harness 的使用者和插件作者提供可独立运行的 TypeScript 插件框架。使用者通过 profile 选择运行组合，通过 bundle 安装和复用一组能力；插件作者可以提供服务、消费服务、发送事件，并在加载、卸载和重载时获得明确结果。

用户已确认：框架名称为 Kongming Harness，简称 `kmh`；运行入口命名为 `kmh`，基础 bundle 命名为 `kmh-base`；使用 profile、bundle 组织；自主定义的品牌、命令、包名、配置名称、服务与事件标识统一采用 KMH 命名体系，名称中禁止出现 `deepseek` 或 `dsh`。Cordis 保留其框架名称，涉及自主分发的包名仍遵守 KMH 命名约束。

用户已确认：基础功能验收可以参考和迁移 DeepSeek Harness 的已有测试用例。迁移后的用例执行 KMH 的真实框架能力，按照本规格核对预期结果，并将自主命名调整到 KMH 体系；参考用例的来源记录保留，覆盖缺口补充 KMH 自己的场景。

本阶段交付插件运行、装配和生命周期闭环。以两个示例插件验证服务依赖、调用、事件和资源释放。Agent 执行、Thread 管理、模型、工具、记忆、工作流、调度、司天、进化以及 React/Tauri 接入属于后续阶段。

用户已确认本阶段范围：`kmh-base` 提供本阶段所需的最小公共框架能力；bundle 管理优先支持本地已准备好的包；启动时要求所有启用的插件完成加载；运行中的配置修改通过显式重载应用。具体规则及场景见文末已确认项。

## feat01: 使用统一的 KMH 名称识别框架

使用者能够从启动入口、帮助说明、运行报告和插件清单中识别同一套框架。

场景1: 查看框架身份
- GIVEN 使用者已经准备好基础框架
- WHEN 使用者查看帮助、版本或启动说明
- THEN 框架名称显示为 Kongming Harness，入口显示为 `kmh`，基础 bundle 显示为 `kmh-base`

场景2: 查看自主分发的组件
- GIVEN 使用者安装了框架提供的包和示例 bundle
- WHEN 使用者查看包名、配置名称及服务与事件标识
- THEN 自主定义的名称遵守 KMH 命名体系，名称中禁止出现 `deepseek` 或 `dsh`

场景3: 检查不合规的自主命名
- GIVEN 插件作者提交的自主组件使用了违反命名约束的名称
- WHEN 作者执行交付检查
- THEN 检查失败，并指出不合规名称及所在位置

## feat02: 创建和选择独立的 profile

使用者可以保存多套运行组合，并明确选择本次运行使用哪一套。

场景1: 创建新的运行组合
- GIVEN 名为 `demo` 的 profile 尚未存在
- WHEN 使用者创建 `demo`
- THEN 创建结果包含 `kmh-base`，使用者可以查看该 profile 并启动它

场景2: 选择已有组合
- GIVEN `demo` 和 `review` 两个 profile 各自保存了插件选择与设置
- WHEN 使用者选择 `review` 启动
- THEN 本次运行采用 `review` 的选择与设置，`demo` 的记录保持原值

场景3: 重复创建
- GIVEN 名为 `demo` 的 profile 已经存在
- WHEN 使用者再次创建同名 profile
- THEN 提示名称已存在，已有插件选择与设置保持原值

场景4: 选择不存在的组合
- GIVEN 指定名称的 profile 尚未存在
- WHEN 使用者直接选择该名称启动
- THEN 启动失败，报告该名称尚未创建，并给出创建入口

场景5: 名称无效
- GIVEN 使用者填写了空名称或带目录跳转含义的名称
- WHEN 使用者创建或选择 profile
- THEN 操作失败，提示允许的名称规则

## feat03: 按 profile 管理 bundle

使用者可以把一组插件及其默认设置作为 bundle 安装、启用、停用和移除。

场景1: 安装本地 bundle
- GIVEN 本地存在准备完整的 `kmh-example` bundle，目标 profile 已创建
- WHEN 使用者将该 bundle 安装到目标 profile
- THEN 安装结果列出 bundle 及其贡献的插件，目标 profile 保存该选择，下次启动加载这些插件

场景2: 只有基础 bundle
- GIVEN profile 只选择了 `kmh-base`
- WHEN 使用者启动该 profile
- THEN 框架显示就绪，业务插件清单为空，使用者可以查看基础能力和停止框架

场景3: 重复安装
- GIVEN 同一 bundle 已安装到目标 profile
- WHEN 使用者再次安装相同来源的同一版本
- THEN 报告该 bundle 已安装，插件选择保持一份

场景4: 停用和再次启用
- GIVEN 目标 profile 已安装一个示例 bundle
- WHEN 使用者停用它并重新启动，随后再次启用并重新启动
- THEN 停用期间其插件显示为停用且参与能力为空，再次启用后其能力恢复，安装记录与用户设置保留

场景5: 移除 bundle
- GIVEN 某个扩展 bundle 已安装在目标 profile
- WHEN 使用者移除它并重新启动
- THEN 该 profile 的安装与运行选择中移除该 bundle，其插件贡献撤回，其他 profile 的选择保持原值

场景6: 安装失败
- GIVEN 目标 bundle 缺少声明的内容、内容无法读取或必要组件尚未准备好
- WHEN 使用者安装该 bundle
- THEN 报告失败原因，目标 profile 保留操作前的安装与运行选择

场景7: 停用或移除基础 bundle
- GIVEN 使用者正在管理 profile 的 bundle 选择
- WHEN 使用者尝试停用或移除 `kmh-base`
- THEN 操作被拒绝，提示该 bundle 是本阶段每个 profile 的必要基础

## feat04: 查看和覆盖最终生效的设置

使用者可以在保留 bundle 默认设置的同时，为单个 profile、本机或本次启动指定自己的完整设置。

场景1: 按层应用设置
- GIVEN 多个 bundle 按指定顺序提供设置，使用者另有 profile 设置、本机共用设置和本次启动设置
- WHEN 使用者查看最终生效的组合
- THEN 按 bundle 顺序、profile 设置、本机共用设置、本次启动设置依次应用，同一插件由较后层的完整设置取代较前层的设置

场景2: 插件的完整设置被替换
- GIVEN 较前层为某插件提供两项设置，较后层只为该插件提供一项设置
- WHEN 使用者查看最终设置
- THEN 较后层的设置整体生效，遗漏项按该插件声明的默认规则处理，必要项缺失时报告错误

场景3: 多次临时覆盖
- GIVEN 使用者为本次启动依次提供两份临时设置
- WHEN 两份设置指向同一个插件
- THEN 后提供的完整设置生效，profile 和本机保存的设置保持原值

场景4: 设置错误
- GIVEN 最终组合包含无法读取的内容、非法值或指向不存在条目的补丁
- WHEN 使用者检查设置或启动框架
- THEN 无法读取或非法的内容报错并指出来源；无法匹配目标条目的补丁警告并跳过，诊断可查询

场景5: 查看组合而保留运行停止状态
- GIVEN 使用者已经准备好 profile 与 bundle
- WHEN 使用者仅要求查看最终组合
- THEN 显示插件选择、启用状态、最终设置及来源，插件业务活动保持停止

## feat05: 根据服务依赖激活插件

插件作者可以声明需要的服务，框架在依赖准备好后激活消费者，并在依赖撤回后暂停消费者。

场景1: 提供者与消费者共同加载
- GIVEN 示例提供者可以提供 `kmh-example-service`，示例消费者声明需要它
- WHEN 两个插件按任意声明顺序加入同一运行组合
- THEN 消费者在服务准备好后激活并完成调用，运行报告显示二者均已激活

场景2: 依赖缺失
- GIVEN 已启用的消费者需要一个当前组合中缺失的服务
- WHEN 使用者启动框架
- THEN 消费者显示为等待依赖，启动报告列出缺失服务，整体启动以失败结束并释放本次已获得的资源

场景3: 撤回和恢复服务
- GIVEN 提供者与消费者均已激活
- WHEN 使用者卸载提供者，随后重新加载提供者
- THEN 消费者先停止并释放自己的资源，服务恢复后重新激活，每项服务与监听保持一份

场景4: 服务名称冲突
- GIVEN 同一服务可见范围内已有一个提供者
- WHEN 另一个提供者尝试提供同名服务
- THEN 后加入的提供者加载失败，报告冲突名称，已有提供者的服务保持可用

场景5: 依赖形成循环
- GIVEN 两个启用的插件各自等待对方提供服务，且其他提供者无法满足依赖
- WHEN 使用者启动框架
- THEN 启动失败，运行报告列出等待关系，使用者可以定位相互等待的插件

## feat06: 通过服务调用和事件协作

插件作者可以调用已声明的服务，也可以通过事件通知其他插件或共同处理一次操作。

场景1: 调用公开服务
- GIVEN 示例消费者已获得示例服务
- WHEN 消费者提交一条示例输入
- THEN 使用者看到提供者返回的对应结果及调用来源

场景2: 向多个插件发送通知
- GIVEN 两个插件均订阅了同一个示例事件
- WHEN 作者触发一次事件
- THEN 每个有效订阅各收到一次通知，使用者能够查看对应记录

场景3: 多个处理者按约定协作
- GIVEN 一次示例操作配置了按顺序处理并交接的插件
- WHEN 每个处理者完成自己的工作并交给后续处理者
- THEN 使用者看到符合声明顺序的处理结果；声明为终止后续处理的结果按约定结束本次操作

场景4: 调用或事件处理失败
- GIVEN 服务调用或事件处理中的插件产生错误
- WHEN 使用者执行该示例操作
- THEN 按该操作声明的处理方式返回失败或报告观察者错误，记录指出产生错误的插件，本次操作终态可查询

场景5: 作者使用了不匹配的调用
- GIVEN 作者使用了未声明的服务、事件名称或不匹配的参数
- WHEN 作者执行开发检查
- THEN 检查指出使用位置与不匹配内容，帮助作者在运行前修正调用

## feat07: 隔离不同插件组的服务与设置

使用者可以在同一个 profile 中为不同插件组选择各自的服务实现和设置。

场景1: 两个插件组使用同名服务
- GIVEN 两个插件组分别准备了名为 `kmh-example-service` 的服务，并分别设置不同的示例返回值
- WHEN 两个组的消费者各调用一次服务
- THEN 每个消费者得到所属组的返回值，调用记录可区分所属组

场景2: 改动一个组
- GIVEN 两个隔离的插件组均在运行
- WHEN 使用者修改并重载其中一个组的服务
- THEN 该组使用新的服务结果，另一个组的结果和设置保持原值

场景3: 当前组依赖缺失
- GIVEN 一个消费者所属组缺少必要服务，另一个隔离组存在同名服务
- WHEN 使用者检查或启动当前组合
- THEN 报告消费者所属组的依赖缺失，并明确指出所属组

## feat08: 加载、卸载、重载并停止运行

使用者可以显式改变插件运行状态，并得到资源清理和再次启动的明确结果。

场景1: 正常卸载
- GIVEN 示例插件已注册服务、事件监听和定期示例活动
- WHEN 使用者卸载该插件
- THEN 卸载完成后该插件的服务与监听撤回，定期活动结束，相关依赖者停止

场景2: 重复重载
- GIVEN 示例插件当前正常运行
- WHEN 使用者连续执行三次重载
- THEN 每次均显示明确结果，每个有效订阅对一次事件只响应一次，定期活动保持一份

场景3: 加载到一半失败
- GIVEN 插件在已经登记一部分能力后发生加载错误
- WHEN 框架处理该失败
- THEN 该次加载已登记的能力撤回，运行报告显示失败插件与原因，修正后可以重新加载

场景4: 运行中修改设置
- GIVEN profile 当前正在运行
- WHEN 使用者修改保存的设置，并执行显式重载
- THEN 重载成功后应用新设置，受影响插件及其依赖者按生命周期重新准备，其他独立插件继续运行；可写条目表中的自有条目经重载回写持久化

场景5: 重载失败
- GIVEN 使用者提供的新组合中有一个插件无法加载
- WHEN 使用者执行重载
- THEN 报告重载失败，失败插件及受影响的依赖者显示失败或等待，其他独立插件继续运行；修正后再次重载可以恢复

场景6: 正常停止框架
- GIVEN profile 正在运行并持有示例活动
- WHEN 使用者请求停止
- THEN 框架停止接收新操作，结束已有活动并释放所属资源，清理完成后报告停止成功

场景7: 清理失败或等待超时
- GIVEN 某插件释放资源时发生错误，或超过使用者配置的等待时限
- WHEN 使用者卸载、重载或停止框架
- THEN 报告操作未完整完成，指出插件和阻塞原因，并以失败结果结束该次管理操作

## feat09: 查看运行状态和失败原因

使用者能够把运行结果追溯到所选 profile、bundle 和插件。

场景1: 查看正常运行状态
- GIVEN 一个 profile 已启动
- WHEN 使用者查看运行状态
- THEN 显示 profile、已选择的 bundle、插件所属来源及其启用、激活、等待、失败或停止状态

场景2: 定位失败
- GIVEN 某个插件加载或运行失败
- WHEN 使用者查看该次失败记录
- THEN 显示所属 profile、bundle、插件、操作阶段和错误原因，依赖问题同时显示缺失服务或受影响插件

场景3: 尚未启动
- GIVEN profile 已创建且当前处于停止状态
- WHEN 使用者查看该 profile
- THEN 显示保存的组合与停止状态，运行状态明确区分已配置和已激活

场景4: 敏感设置的展示
- GIVEN 某项设置被插件声明为敏感值
- WHEN 使用者查看最终设置、运行状态或失败记录
- THEN 使用掩码展示该值，其他可用于定位问题的信息正常显示

## feat10: 用示例 bundle 验收基础框架

使用者通过一个示例 bundle 完整观察 profile、bundle、服务依赖、事件、隔离和生命周期的协作。

基础测试参考入口包括 [profile 创建、bundle 层顺序和运行组合](../../../../agent/deepseek-harness/packages/boot/app-boot/tests/profile.spec.ts)、[配置读取、服务依赖满足与提供者替换](../../../../agent/deepseek-harness/packages/boot/app-boot/tests/user-patches.spec.ts)以及 [插件设置修改与失败处理](../../../../agent/deepseek-harness/packages/boot/plugin-manager/tests/patch.spec.ts)。这些位置用于后续挑选行为用例，参考范围按本阶段功能逐项筛选。

场景1: 跑通正常示例
- GIVEN 使用者创建了 `demo` profile 并安装 `kmh-example` bundle
- WHEN 使用者启动并提交示例输入
- THEN 示例提供者和消费者完成服务调用与事件通知，结果中能够识别输入、提供者、消费者和所属运行组合

场景2: 基础空组合
- GIVEN 使用者只加载 `kmh-base`
- WHEN 使用者查看运行状态
- THEN 能确认框架就绪、业务插件为空，并执行正常停止

场景3: 验收隔离与重载
- GIVEN 两个示例组使用不同返回值，示例插件已运行
- WHEN 使用者分别调用两个组，并反复卸载和重载其中一个提供者
- THEN 两组结果始终对应各自设置，依赖者停止与恢复可观察，一次事件保持每个有效订阅一次响应

场景4: 验收失败与恢复
- GIVEN 示例提供者被配置为加载失败
- WHEN 使用者启动并查看失败报告，随后修正设置并重新启动
- THEN 第一次得到明确失败与资源清理结果，第二次完成正常示例，记录能够区分两次操作

场景5: 迁移已有基础测试
- GIVEN 作者选定了参考框架中与本规格对应的基础测试用例
- WHEN 作者将用例接入 KMH 并执行验收
- THEN 用例实际运行 KMH，使用 KMH 的自主名称，验收记录能够追溯参考用例、本规格场景及本次运行结果

场景6: 处理参考用例与 KMH 的行为差异
- GIVEN 参考用例的原有预期与本规格的已确认行为存在差异，或本规格场景尚无参考用例
- WHEN 作者准备并执行 KMH 验收
- THEN 差异用例按照 KMH 规格调整并记录依据，覆盖缺口补充对应场景，报告区分已通过、失败和待验证的场景

## 已确认项

- **本阶段基础范围**：概述、feat03 场景2、feat10 场景2 已确认 `kmh-base` 只提供最小公共框架能力；Agent 与业务功能在后续阶段加入。
- **profile 创建规则**：feat02 场景1、场景4 已确认显式创建时加入 `kmh-base`，启动未知 profile 时提示创建。
- **bundle 来源与基础选择**：feat03 场景1、场景7 已确认优先支持本地准备好的 bundle，每个 profile 的 `kmh-base` 固定启用；远程获取和版本升级另列后续需求。
- **配置覆盖顺序**：feat04 场景1至场景3 已确认 bundle 顺序、profile、本机、本次启动依次覆盖，同一插件完整设置整体替换；v0.2 起各层统一为补丁文档语义（insert 插入、按 id 覆盖、name 校验），后层可定位并调整前层插入的条目。
- **启动严格度**：feat05 场景2、场景5 已确认所有启用的插件都必须准备好，等待依赖与加载失败均导致整体启动失败。
- **重载方式与失败结果**：feat08 场景4、场景5 已确认显式重载，失败插件和受影响依赖者停止，独立插件继续运行；重载经所属条目树提交（diff 重挂载 + 可写条目表回写）；自动监听配置与源码变化另列后续需求。

## v0.2 附录：配置体系对齐参考框架

用户已确认 v0.2 将配置体系重新参照 DeepSeek Harness 实行，差异点按本附录执行：

- **运行时底座**：`@kmh/runtime` 改为驱动官方 `@cordisjs/plugin-loader`（1.0.0-rc.7）与 `@cordisjs/plugin-include`（1.1.0）；条目模型对齐官方 `EntryOptions`（id/name/config/group/disabled/inject/intercept/isolate），隔离按服务声明（`true` 为条目私有、字符串为命名共享域）。
- **组合形态**：bundle 与各覆盖层统一为补丁文档（与官方 include 补丁语义一致：insert 插入根或指定 group、按 id 覆盖任意键、name 校验防错配、后层可定位前层插入的行）；profile 目录保存 `profile.yml`（安装记录）、`cordis.yml`（可写条目表，运行期配置修改回写于此）与 `cordis.patch.yml`（用户补丁层）；本机层 `config.yml` 与 `--patch` 启动层同为补丁文档。
- **插件形态**：插件为标准 Cordis 函数插件（name/inject/provide/Config/apply 静态），配置 schema 走 Standard Schema V1（KMH 使用 zod），条目省略 config 时按空对象解析默认值；`sensitive` 敏感路径作为 KMH 扩展静态声明。
- **组合校验**：无法匹配目标条目的补丁警告并跳过（诊断可查询）；同一组合内重复插件 id 报错。
- **清理语义**：资源清理错误按官方 fiber 语义被包容，KMH 通过诊断事件通道归属记录；停止时先逐条目回收再回收根实例以保留诊断可达。

用户已确认工程约束：所有新增实现、示例、测试与检查脚本均写入 `packages/`；每个函数使用中文注释，说明职责、关键输入和输出；每个代码文件顶部说明文件作用、关键流程及关键函数。
