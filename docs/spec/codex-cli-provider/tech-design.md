# Codex 会话新建与复用：最小修改方案

> 设计状态：已确认；版本 v0.3，2026-10-13。
> 编写依据：已确认的 [spec.md](spec.md)，具体版本与确认记录见[追溯附录](#trace)。
> 本轮范围：主助手按新版 x-tech-design 重组上一版方案；只修改本文，代码改动范围保持原方案。

## 本轮设计差异

当前 `tool-policy.ts` 每回合重新读取工具开关；`adapter.ts` 会因为工具策略存在或目录变化而重新创建 Codex 会话，还会把历史逐条裁到 600 字后传入。方案沿用现有配置、会话绑定文件和官方 CLI 接口，修改工具配置的读取时机与新建/恢复的判断。具体源码和改动位置见[追溯附录](#trace)。

## 工具开关：新会话采用当前选择，老会话保持原选择

对应 spec 的“工具与技能隔离”。本节只修改工具选择的生效时机；技能沿用已确认的独立规则。

<a id="d01"></a>
<a id="tools-create"></a>

### 方案与理由

创建 KMH 会话时，Codex 插件读取一次当前工具开关，筛出打开的工具，保存一份独立副本。首次创建 Codex 会话时传入这份工具列表。这样，创建后再改开关，已有会话仍使用创建时的选择。

<a id="d03"></a>
<a id="tools-execute"></a>

### 数据流与执行检查

`index.ts` 接收 KMH 现有的创建通知 → `tool-policy.ts` 读取配置并筛选 → 用[会话绑定文件](#binding-data)保存 → 首次发送时交给 Codex。保存失败明确报错；重试继续使用已取得的副本。默认配置由 Codex 插件拥有，Selector 的职责见[配置编辑](#selector-edit)。

续聊的工具列表和执行检查都读取这份保存值。配置里后来关闭 C，老会话的 C 仍可执行；后来打开 D，老会话仍没有开放 D。新工具、显示名称和排序变化保持老选择。工具程序实际被卸载时明确报告不可用，审批和权限继续走已有流程。

### 测试场景与预期

这些测试拟使用真实插件和官方 CLI，配合本机测试服务记录模型请求、session ID 与工具执行次数；同时覆盖 KMH 工具和 Codex 原生工具。当前均为测试计划。

<a id="t3"></a>

#### 修改工具开关后，老会话继续使用原工具

打开 A、B、C，关闭 D，创建甲并发送消息，记下 Codex 的会话编号 S1；再关闭 C、打开 D，续聊甲；然后把开关全部关闭，再续聊甲。每轮结束均让 CLI 进程退出。

预期：甲始终使用 A、B、C，C 的真实调用成功，D 的强制调用被拒绝且执行次数为 0；每次都恢复 S1，重启 CLI 所需的工具设置也取保存值。检查业务新建请求只有第一次发出，工具列表只在那次创建时传入。禁止根据新开关重新声明工具、新建或分叉甲、回灌旧聊天。工具调用测试取实际执行结果，界面开关不能代替这项证据。

<a id="t2"></a>

#### 关闭工具后，新建会话使用修改后的选择

按 spec 的甲、乙场景，在甲创建后关闭 C，再普通新建乙。预期：乙传入的工具只有 A、B，得到独立会话编号 S2；甲仍使用 S1 和 A、B、C。检查实际创建请求和模型工具列表，禁止把乙的配置写回甲。

<a id="t1"></a>

#### 创建后、首条消息前改开关，仍使用创建时的选择

打开 A、B、C，创建甲但暂不发消息；关闭 C 后再发送甲的首条消息。预期：创建 Codex 时仍传 A、B、C。收到编号后先保存，再发送任务；注入保存失败时，任务明确报错并保持未发送。禁止到首条消息才读取最新开关。检查创建通知、文件写入与 CLI 请求的先后顺序。

## 持续对话：新建保存编号，续聊恢复原会话

对应 spec 的“持续对话与会话绑定”。Codex 的 session ID 是它保存的对话编号，以下用 S1 表示；插件把这个编号和 KMH 会话对应保存，继续聊天时才能恢复同一份历史。

<a id="d02"></a>
<a id="binding-data"></a>

### 保存哪些数据，为什么沿用现有文件

复用 `session-store.ts` 的 `codex-bindings.json`，在每个 KMH 会话的原记录里补存工具信息。现有文件已经负责保存 Codex 编号和聊天处理位置，补字段就能把原工具与原编号一起读回。记录由 Codex 插件读写；未来默认值仍来自插件配置。

| 保存内容 | 本轮处理 |
|---|---|
| 原工具信息，新增 | 打开的 KMH 工具名称、来源、参数说明、已有调用名称对应关系，以及 Codex 原生工具四项开关；技能按现有独立规则读取 |
| Codex 会话编号 | 沿用 `threadId` 字段；首次收到编号前可空，收到后保存，续聊必须使用原值 |
| 聊天处理位置 | 沿用现有指纹和完成回合记录；更新时保留原编号与工具信息 |

文件中的新增字段在 `session-store.ts` 校验；内存副本只缓存已保存的记录，重启后从文件读取。文件写入沿用临时文件改名方式，写入按顺序执行，成功后更新内存。这里沿用现有保存文件，是本轮推荐方案；代价是旧记录可能缺少工具信息，其处理见[恢复失败](#recovery-failure)。

<a id="d04"></a>
<a id="session-resume"></a>

### 新建、续聊的数据流

首次发送：`adapter.ts` 读取保存的工具 → `turn.ts` 调用官方新建接口 `thread/start` → 收到编号 → `index.ts` 保存编号 → 完整发送任务。官方请求中的 `dynamicTools` 表示交给 Codex 的 KMH 工具声明，只在新建时传入。

已有会话续聊：读原编号和工具 → 拉起本轮 CLI → 调用恢复接口 `thread/resume(S1)` → 完整发送本轮新增输入。Codex 自己续用历史和压缩结果。删除“有工具策略就重建”“目录变化就重建”和普通续聊里裁成 600 字回灌历史的处理；官方请求及响应定义沿用 [protocol.ts](../../../packages/codex-cli/src/protocol.ts)。

会话操作沿用现有排队、取消、超时与进程回收。收到编号后保存失败时，本次任务停止；普通恢复响应若返回不同编号，按恢复错误处理。每轮任务保持单次执行，按[持续对话与会话绑定](spec.md#feat03-持续对话与会话绑定)的规则推进。同一会话的工具执行保持已有单次执行规则。

<a id="d08"></a>
<a id="recovery-failure"></a>

原编号不存在、文件损坏或旧记录缺少原工具信息时，保留记录并说明恢复失败。禁止自动新建替代 S1、用当前开关猜旧选择。用户可普通新建会话开始新任务；这项旧数据处理代价随保存方案一起审阅。

<a id="d09"></a>
<a id="progress-recording"></a>

详细工具日志按 CLI 实际提供的信息记录，继续显示可提供的进度与结果。日志能力有限时保留 S1 和原历史，禁止为补日志重新创建会话。

<a id="d05"></a>
<a id="session-fork"></a>

分叉、编辑、重发沿用源会话工具，并通过官方 `thread/fork` 继承历史，再完整发送新增或编辑输入。禁止读取最新开关替换源选择、重复发送已继承历史。现有 CLI 提供回合前后的位置；工具调用内部的精确分叉位置仍待核实，这部分保持单独未验证状态。

### 测试场景与预期

本功能同时引用[修改开关后复用](#t3)、[新建会话采用新选择](#t2)、[首条消息前修改开关](#t1)：分别核对恢复编号与新建次数、父子会话编号独立、保存编号先于任务发送。工具集合与执行结果的断言仍在各自主定义里，避免重复维护。

<a id="t4"></a>

#### KMH 重启后，继续恢复原编号和原工具

修改开关后重启 KMH，再续聊甲。预期：从现有文件恢复 S1 和 A、B、C；禁止重新取全局开关替换甲。拟用真实插件冷启动，检查读取文件、CLI 恢复请求和模型工具。

<a id="t5"></a>

#### 原会话或保存记录缺失时，明确失败并保留数据

分别移走原 Codex 会话、提供损坏文件、提供缺少工具信息的旧记录。预期：明确说明恢复失败，原记录保留；新建请求次数为 0。拟用文件故障测试，禁止把错误当全新会话或用最新开关补造旧工具。

<a id="t6"></a>

#### 长消息完整送达，旧聊天保持单份

在已有甲中发送超过 600 字、末尾带任务标记的消息，再退出进程并继续。预期：标记完整到达 Codex，旧输入在原生历史中保持单份；禁止截断或回灌历史。拟核对官方 CLI 请求与原生历史，图片按已有支持范围回归；实际模型的长上下文压缩仍需单独运行取证。

<a id="t11"></a>

#### 详细工具日志有限时，仍恢复原会话

恢复时只提供普通进度通知。预期：S1、原工具与历史保持，显示实际可提供的信息；禁止为日志换会话。拟使用官方 CLI 恢复并核对编号和通知。

<a id="t17"></a>

#### 修改开关后分叉，子会话继承源工具与原生历史

修改全局开关后分叉甲。预期：子会话沿用甲的工具，父编号保留，继承历史只出现一次；禁止取最新开关。拟用现有分叉入口和官方 CLI 检查请求、父子记录与历史；精确事件位置另核实，失败或未验证均保持该状态。

<a id="t18"></a>

#### 修改开关后编辑或重发，源工具保持，编辑输入只发一次

修改全局开关后编辑或重发甲的历史消息。预期：沿用源工具，按编辑位置原生分叉，完整编辑输入只发一次；禁止重复灌入已继承历史。拟核对现有编辑入口、官方分叉请求与实际输入；精确位置的能力限制同[分叉方案](#session-fork)。

## 插件详情页：Selector 编辑默认开关，Codex 独立执行

对应 spec 的“插件详情页”。工具开关的执行归属和恢复规则由 Codex 插件负责。

<a id="d07"></a>
<a id="selector-edit"></a>

### 方案、职责与失败处理

Selector 通过已有配置入口展示和保存默认开关，提示“工具开关仅对普通新建会话生效”。Codex 自己读取配置、筛选工具、保存会话和恢复；共享工具目录的注册改为可选，准备失败直接报错。这样 Selector 启停只影响编辑界面。

依赖方向保持为 Selector 调用已有配置接口；Codex 执行直接使用自身记录，通过公开插件接口接入 KMH。字段校验沿用共享选择定义，客户端提示走现有本地化入口。界面提示修改只涉及[本节功能](spec.md#feat05-插件详情页)，账号、模型、登录与连接测试沿用原实现。

### 测试场景与预期

<a id="t8"></a>

#### 关闭 Selector 后，Codex 仍能新建和续聊

关闭或卸载 Selector，通过 Codex 配置修改工具开关，再新建乙和续聊甲，最后重新启用 Selector。预期：乙采用新选择，甲恢复原编号与工具，重新启用后展示已保存的当前配置；界面正确说明生效范围。禁止等待 Selector 才执行，禁止把默认编辑写回甲。拟用真实 profile 装卸和 Web 操作，分别核对配置保存、业务请求与提示文案。
