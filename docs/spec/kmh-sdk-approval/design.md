# 动态模型

本页为拟议实现的动态设计。决策唯一归属为 [modules.md 的关键决策](modules.md#关键决策)，用户验收归属为 [spec.md 的验收](spec.md#验收)。当前只记录方案。

## 数据流

DSH 工具或扩展发起 ctx.approval.request。DSH 审批服务执行策略判定并记录 approval/asked，再将审批事件送入应答链。KMH 桥接确认归属，通过唯一 transport 向客户端发送 approval/ask；客户端回调作出决定，桥接校验 outcome，DSH 服务提交 approval/decided 并向原调用者返回结果。对应 D1、D2、D3、D4。

审计记录由 DSH 保存。KMH 只保存连接存续期间的待决请求、会话归属和取消控制器；displayReason 作为展示字段传递。并发关联使用独立请求身份，sessionId 和 callId 承担定位用途。

## 状态流转

承载维护创建、就绪、关闭中的连接状态。审批维护待发送、等待客户端、已允许、已拒绝、已取消、不可用的请求状态。每次请求只能结算一次；取消获胜后，晚到应答保留失效状态。客户端重连后的未决请求以重新发起的身份处理，跨连接恢复属于延后范围。

会话归属区分首个任务登记中、已登记、登记失败与关闭。实际 Agent 身份与连接登记共同决定可应答范围；首版仅允许根会话。子 Agent 的传递范围、父会话身份和独立审批卡片需后续评审。

## 时序

KMH profile 将官方 SDK 服务条目替换为 KMH 承载入口，同一 stdio 连接由该入口独占。initialize 等待 Loader 就绪；session/prompt 的归属登记与任务开始之间有明确同步点；服务端审批和客户端应答保持双向独立处理，审批等待期间仍可关闭连接。对应 D2、D3。

插件卸载先停止接受新请求，撤回监听、取消待决请求，再释放 SDK 服务与 transport。协议 shutdown 保留响应写出与 flush、根运行时关闭、进程退出的既有顺序。实现需要验证这两个释放路径的幂等性与等待行为。

## 资源

KMH 承载拥有 transport 和连接关闭控制器，DSH SDK 服务类拥有其创建的 Agent handles。桥接拥有监听 disposer 和每次请求的取消控制器；客户端拥有自己的 transport 和回调任务。通过 ctx.effect、ctx.on 和 transport 公共取消能力释放资源。对应 D2、D3、D4。

拟议 Config 包含审批等待超时和待决请求容量；默认值需评审。资源上限耗尽、超时和连接关闭必须结束对应等待，DSH 审批结果保持安全停止。日志归入 KMH_HOME 的既有日志体系，stderr 保存诊断，stdout 保存协议帧。

## 故障与恢复

| 触发 | 拟议处理 | 后续验证 |
|---|---|---|
| 其他入口创建的会话 | 桥接调用 next()，交还所属应答链 | 归属与跨会话隔离 |
| 无效 outcome、客户端拒绝处理或传输失败 | 桥接调用 next()，由 DSH 链决定 unavailable 等结果 | 无效载荷与断开 |
| 请求 AbortSignal 取消 | DSH 判 cancelled，桥接放弃传输等待并清理本地资源 | 取消与晚答复竞争 |
| 插件卸载、根运行时关闭 | 撤回监听、终止待决请求、释放服务与连接 | 重复加载与双重关闭 |
| 首个任务登记失败 | 清理临时归属，保留错误并阻止错误路由 | 首个 prompt 与重复 sessionId |
| 永不允许策略 | DSH 服务直接返回 rejected | 客户端应答保持策略约束 |

客户端待决卡片的撤销通知需要与请求身份一起评审。暂定选择为每次请求增加 KMH approvalId，并定义独立撤销通知；字段与通知方法将在协议评审后稳定。对端缺少审批应答能力时按传输错误处理。对应 D1、D4。

## 迁移

实施从方案评审开始，完成条件由需求页场景判定。

1. 明确首版客户端载体、会话归属同步点、撤销通知、超时与容量，并对齐流程文档版本。
2. 在 KMH 建立自有协议、承载、桥接与客户端适配，通过 profile 选择 KMH 插件，保持 DSH 公共源码版本。
3. 验证真实 stdio 会话、一次允许、拒绝、取消、无效结果、断开、并发隔离、never 策略、首个 prompt、卸载与正常 shutdown。验证使用确定性本地工具触发审批，接通客户端回调与真实 transport；具体产品界面另行验收。
4. 保存独立 DSH 草稿的源码、测试与 tracked diff。当前 stash 只保存 tracked 部分，approval.spec.ts 需要单独保留。
5. KMH 端到端验收后，撤回独立 DSH 中 types.ts、server.ts、package.json、原测试与锁文件的审批修改，并移除已经迁移的新审批测试。撤回前逐文件核对当时 diff，保留期间新增的其他工作。
6. 回滚通过 KMH profile 恢复官方 SDK 服务条目，并保存 KMH 插件和草稿材料；稳定运行回归后再处理备份保留期限。

后续实施影响面为 packages/sdk-approval/、profiles/kmh-sdk/、KMH 自有测试与使用文档。当前文件写入限于本方案包与文档导航。

## 开发备注

本节记录待评审事项，技术选择以 modules.md 的决策记录为依据。

- 首版根会话范围和应答回调来自 J4 暂定默认；具体 Web、手机、Python 接入范围待用户确认。
- 会话登记同步点需用 DSH 公共接口完成，并验证首个 prompt、失败重试与 Agent 身份。私有状态访问和 transport 并行读取均属于排除方案。
- 撤销通知的 approvalId、方法名、超时与容量默认值待评审。
- 本轮使用 x-spec2 的 V2 三文件模板。当前安装的 xdev 校验器要求 V3，x-req 技能正文接受 feat 场景格式；实施前需要统一流程版本。本文档包保持探索中，当前开放程度仅为方案评审。

后续流程按“方案评审与格式对齐 → x-req 任务拆解 → x-dev 开发 → x-verify 交付对账 → x-qa-gate 审查”推进。本轮只执行记录与文档核对。
