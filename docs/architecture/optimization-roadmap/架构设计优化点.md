结论：你现在的方向是对的，接近 **模块化单体 Modular Monolith + Facade 边界类**。它很适合你这种单人维护、项目逐渐庞大、又需要架构清晰的 agent 框架。

但它的风险是：**模块边界会越来越像“组织代码的盒子”，而不是“表达业务流的结构”**。如果只按模块拆，而没有主流程、依赖方向、扩展点约束，后期仍然会散。

---

## 1. 你当前设计的本质是什么

你说的：

> 模块化设计，高内聚低耦合，模块内功能由边界类提供访问

本质上是：

```txt
外部模块
  ↓
ModuleBoundary / Facade
  ↓
模块内部 service / repository / model / runner / util
```

例如：

```txt
SessionBoundary
  - create_session()
  - append_message()
  - get_context()
  - close_session()

ToolBoundary
  - register_tool()
  - execute_tool()
  - get_tool_schema()

ApprovalBoundary
  - check_action()
  - request_approval()
  - record_decision()
```

这个设计的好处是明显的：外部不需要知道模块内部细节，模块内部可以重构，外部调用稳定。对 agent 框架这种长期演化项目来说，这是非常重要的。

---

## 2. 这种设计的主要坏处

### 第一，边界类容易变成“上帝类”

一开始边界类只是提供入口：

```python
session.create()
session.get()
session.update()
```

后面需求越来越多，容易变成：

```python
session.create_thread()
session.create_agent_thread()
session.bind_workspace()
session.load_memory()
session_export_markdown()
session_replay()
session_debug_trace()
session_attach_tool_call()
session_restore_from_crash()
```

结果边界类越来越厚，最后它不是“边界”，而是一个新的大泥球。

解决方式是：**边界类只暴露稳定能力，不承载复杂流程**。复杂流程放到 `use_cases` 或 `application services` 里。

例如：

```txt
session/
  boundary.py              # 稳定对外 API
  use_cases/
    create_thread.py
    restore_thread.py
    export_thread.py
  domain/
    session.py
    thread.py
  infra/
    session_store.py
```

边界类可以调用 use case，但不要自己塞满业务逻辑。

---

### 第二，模块内聚了，但业务流程可能被切碎

agent 框架的核心不是“模块”，而是“执行流”。

例如一次 agent 执行可能跨越：

```txt
Thread → Runtime → Model → Tool → Approval → FileSystem → Memory → Summary → UI Event
```

如果你只看模块，会觉得每个模块都很干净；但真正调 bug 时，你要在 8 个模块之间跳来跳去。

所以仅有模块化不够，还需要一层 **流程视角**。

你应该明确几个主流程：

```txt
1. 创建工作区
2. 创建 thread
3. 启动 agent run
4. LLM 产生 action
5. 审批系统判断
6. 工具执行
7. 结果写入 session
8. 触发观察者/总结/前端事件
```

然后每个流程都应该有一个明确的编排者，例如：

```txt
AgentRunOrchestrator
ToolExecutionOrchestrator
ThreadLifecycleService
ApprovalDecisionService
```

模块解决“归属问题”，流程解决“理解问题”。

---

### 第三，过度抽象会让单人项目变慢

高内聚低耦合很容易被 AI 写成这样：

```txt
interfaces/
services/
managers/
providers/
factories/
registries/
contexts/
adapters/
handlers/
```

看起来很架构，其实每次改一个功能都要跳 7 层。

单人维护项目最忌讳这种“企业级幻觉”。你需要的是：

```txt
少量稳定抽象 + 明确依赖方向 + 可读的主流程
```

不是每个类都配一个 interface，也不是每个功能都建 provider/factory。

建议规则：

```txt
只有当一个东西存在两个以上实现，才抽象 interface。
只有当一个流程被复用，才抽 use case。
只有当外部模块真的要调用，才进 boundary。
只有当未来要替换底层技术，才加 adapter。
```

---

### 第四，边界类可能掩盖隐性耦合

表面上模块之间只通过 Boundary 调用：

```txt
Runtime → ToolBoundary
Runtime → ApprovalBoundary
Runtime → SessionBoundary
```

看起来低耦合。

但如果 Runtime 知道太多细节，比如：

```txt
某个 tool 的特殊状态
某个 approval 的内部枚举
某个 session 的存储格式
某个 memory 的压缩策略
```

那还是耦合，只是藏在参数和返回值里。

判断方式很简单：如果一个模块的内部字段变化，会迫使多个外部模块修改，那边界没有真正隔离成功。

边界 API 应该暴露“业务语义”，不要暴露“内部结构”。

不好：

```python
approval.check(path, command, rule_tree, workspace_policy_json)
```

更好：

```python
approval.decide(action_request)
```

## 3. 除了你当前模式，还有哪些适合 agent 框架的架构模式

我建议你重点看这 4 种，不需要全学，知道它们解决什么问题即可。

### 1. 模块化单体 Modular Monolith

这是你当前最应该采用的主架构。

它不是微服务，也不是散装脚本，而是在一个进程/一个仓库里做强模块边界。

适合你，因为：

```txt
单人维护
项目还在快速变化
需要清晰边界
不想引入分布式复杂度
未来可以局部拆插件
```

推荐作为 xspace / kongming-agent 的主结构。

---

### 2. 六边形架构 Hexagonal Architecture

核心思想是：

```txt
核心业务不依赖外部技术
外部技术通过 adapter 接进来
```

对你的 agent 框架很有用。

例如：

```txt
核心层：
  AgentRuntime
  Thread
  ApprovalPolicy
  ToolCall
  Workspace

适配器：
  ClaudeCodeAdapter
  OpenAIAdapter
  FileSystemAdapter
  TauriAdapter
  WebSocketAdapter
  SQLiteAdapter
  MCPAdapter
```

这样未来你换 Claude、Codex、OpenAI、本地模型、Tauri 插件、Web 版本，都不会把核心逻辑搅乱。

你现在最需要防止的是：

```txt
核心 Runtime 里直接写死 Claude Code SDK
核心 Tool 系统里直接写死 WebSocket
核心 Session 里直接写死 SQLite 表结构
```

六边形架构可以解决这个问题。

---

### 3. DDD 的限界上下文 Bounded Context

DDD 不一定要完整引入，但“限界上下文”非常适合你。

你的项目不是只有技术模块，而是有不同业务领域：

```txt
Workspace 上下文
Thread / Session 上下文
Agent Runtime 上下文
Tool System 上下文
Approval / Policy 上下文
Memory / Context 上下文
Observation / Sitian 上下文
UI Sync 上下文
```

每个上下文有自己的语言。

例如不要混用：

```txt
session
thread
task
workflow
run
message
event
```

你需要定义清楚：

```txt
Workspace：项目级容器
Thread：一次持续对话/任务线
Run：一次 agent 执行
Step：Run 内的一次模型/工具/审批步骤
Task：用户目标或 pipeline 节点
Event：系统状态变更
```

DDD 的价值不是复杂建模，而是防止命名混乱。

---

### 4. Pipeline / Workflow Architecture

agent 框架天然适合流程架构。

例如：

```txt
Input
  ↓
Context Build
  ↓
LLM Plan
  ↓
Action Parse
  ↓
Approval
  ↓
Tool Execute
  ↓
Observation
  ↓
Memory Write
  ↓
Next Step / Finish
```

这类流程不应该散落在各个模块里，而应该被显式建模。

你可以有：

```python
class AgentRunPipeline:
    def run(self, request: AgentRunRequest) -> AgentRunResult:
        context = self.context_builder.build(request)
        decision = self.model_runner.run(context)
        action = self.action_parser.parse(decision)
        approval = self.approval.decide(action)
        result = self.tool_executor.execute(action, approval)
        self.session_writer.write(result)
        return result
```

这会极大降低你的心智负担。

因为你不是靠记忆理解项目，而是靠主流程代码理解项目。

---

## 4. 我建议你的最终架构：模块化单体 + 六边形 + 显式流程

不要搞太复杂。你的 agent 框架可以用这套组合：

```txt
模块化单体：负责代码归属
六边形架构：负责隔离外部技术
显式 Pipeline：负责表达 agent 执行流
边界类 Facade：负责模块间访问
```

可以长这样：

```txt
src/
  kongming/
    core/
      runtime/
        boundary.py
        agent_run_pipeline.py
        step_executor.py
        domain.py

      session/
        boundary.py
        thread_lifecycle.py
        session_store.py
        domain.py

      tools/
        boundary.py
        tool_registry.py
        tool_executor.py
        domain.py

      approval/
        boundary.py
        policy_engine.py
        decision_service.py
        domain.py

      workspace/
        boundary.py
        workspace_service.py
        domain.py

      memory/
        boundary.py
        context_builder.py
        memory_store.py
        domain.py

    adapters/
      llm/
        claude_code_adapter.py
        openai_adapter.py
        codex_adapter.py

      storage/
        sqlite_session_store.py
        file_workspace_store.py

      ui/
        websocket_event_publisher.py
        tauri_bridge.py

      tools/
        filesystem_tool_adapter.py
        shell_tool_adapter.py
        mcp_tool_adapter.py

    apps/
      cli/
      web/
      desktop/
```

关键依赖方向：

```txt
apps → core → ports/interfaces
adapters → core ports
core 不反向依赖 apps/adapters
```

也就是：

```txt
CLI 可以调用 core
Web 可以调用 core
Tauri 可以调用 core
Claude Adapter 可以接入 core

但是 core 不应该知道自己运行在 CLI、Web、Tauri 里
```

这对你后面合并 xspace 和 kongming-agent 很重要。

---

## 5. 你单人维护时，最应该守住的架构原则

你不用追求“完美架构”，只要守住这 5 条。

### 1. 主流程必须一眼看懂

比如打开一个文件就能看到：

```txt
AgentRunPipeline
```

里面表达完整执行链路。

这是项目的脊柱。

---

### 2. 模块只能通过 boundary 互相访问

禁止这样：

```python
from approval.policy_engine import xxx
from session.session_store import xxx
```

允许这样：

```python
from approval.boundary import ApprovalBoundary
from session.boundary import SessionBoundary
```

但 boundary 不能膨胀成上帝类。

---

### 3. 外部技术必须放 adapters

这些都不要进入 core：

```txt
Claude Code SDK
OpenAI SDK
FastAPI
WebSocket
Tauri
SQLite 具体实现
MCP client
文件系统细节
```

core 只认识抽象能力：

```txt
ModelPort
ToolPort
SessionStore
EventPublisher
WorkspaceStore
```

---

### 4. 领域命名要稳定

你需要先定一套核心名词，不然项目会越来越乱。

我建议：

```txt
Workspace：项目空间
Thread：任务/对话线
Run：一次 agent 执行
Step：一次执行步骤
Message：对话消息
Action：模型请求执行的动作
ToolCall：工具调用
ApprovalDecision：审批结果
Artifact：执行产物
Event：系统事件
```

不要今天叫 task，明天叫 workflow，后天叫 session，最后自己也分不清。

---

### 5. 每个模块都写一份 README

每个模块只写 5 个内容：

```txt
1. 这个模块负责什么
2. 不负责什么
3. 对外暴露哪些 boundary
4. 依赖哪些模块
5. 典型流程是什么
```

这个比写大量设计文档有效。

尤其是 AI 参与开发时，模块 README 是给 AI 的“边界提示词”。

---

## 最直接的建议

你现在不要换成复杂架构，也不要上微服务。你的最佳路线是：

```txt
继续模块化单体
保留边界类
给 agent 执行流加 Pipeline/Orchestrator
用 adapters 隔离 Claude/Codex/Tauri/Web/SQLite
用稳定领域名词统一 Workspace/Thread/Run/Step/Task
```

一句话概括：

> 模块化解决“代码放哪里”，Pipeline 解决“系统怎么跑”，六边形解决“外部技术怎么换”，DDD 名词解决“人脑怎么理解”。

你现在缺的不是“更多设计模式”，而是把这四件事叠起来，形成一套项目内的架构纪律。
