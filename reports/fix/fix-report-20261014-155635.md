# Tool Selector 悬空依赖解除（阶段 A）修复报告

> 修复时间：2026-10-14 15:56
> 修复人：Claude (x-fix，bug-fix 模式)

## Bug 描述

Tool Selector 功能曾通过直接修改 DSH 原生源码实现（35 个原生文件 + DSH 内新增 4 个包：`packages/llm/cli-tools`、`packages/api/cli-tools-controller`、`packages/client/ui-cli-tools-selector`、`packages/bundle/harness-cli-tools-selector`），违反「禁止修改 third_party/dsh」约束。2026-10-14 实地核查：原 KMH 子模块与独立维护仓中这批改动已被整体清除，从未提交、无 stash 或分支可恢复；但 kongming-os 迁入的代码仍引用已消失的 `@deepseek-ai/dsh-cli-tools`：

- `packages/codex-cli/package.json:93` 与 `pnpm-lock.yaml` 指向不存在的 `link:../../third_party/dsh/packages/llm/cli-tools`，`pnpm install --frozen-lockfile` 直接失败；
- `packages/codex-cli` 的 config、tool-policy、session-store、native-tools/catalog、client/ToolRecords 共 5 个文件 import 该包；
- `bundles/dsh-web/cordis.patch.yml:20` 与 `profiles/kmh-mobile-assistant` 声明了 `cli-tools` 插件，cordis 启动时解析包名失败。

用户裁定：该功能的职责仅限于可视化 codex-cli 的 tools 配置开关、展现在 codex-cli 插件详情里；工具管理的执行点为 codex-cli 插件读配置、拉起真正 CLI 时只传过滤后的工具（既定方案，不再讨论）。

## 根因分析

`dsh-cli-tools` 不是上游 DSH 的包，而是违规改动本身的产物；peerDependencies 中的 `0.2.1-alpha.1` 只是与其他 dsh-* 对齐的版本线，并无发布物。即使把 4 个包搬进 kongming-os 也无法复活，因为其运行时支撑全在 DSH 原生补丁里，固定子模块提交（`be34e35b39`）中均不存在：

| 原依赖的原生补丁能力 | 固定版核对结果 | 本次采用的公开替代 |
| --- | --- | --- |
| `agent/request-tools` waterfall（逐请求组装工具） | agent / agent-loop 源码零匹配 | `agent/request` waterfall：在 `prepareRequest()` 阶段、用户消息提交之前派发，与原补丁同位置 |
| `ctx.tools.inventory()` / `registeredInventory()` / `presentation()` | 不存在；固定版只有 `register/restrict/guard/get/schemas` | `tools.schemas(scope)` 枚举，`tools.get(name, scope)` 比对参数漂移，`tools.guard()` 拒绝 |
| `register()` 来源追踪（插件来源 id） | 不存在 | 放弃来源标签，harness 行 `source` 固定为 `harness`，按名称回退匹配旧配置 |
| `known-event-types` 登记的 3 个 cli-tools 会话事件 | 不存在 | 事件连同消费它们的会话时间线卡片一并移除（超出可视化职责） |
| settings `schema.ts` 递归复制 | 固定版为浅复制 | 不依赖 schema JSON 往返校验 |

执行点迁移的关键事实：固定版 agent-loop 在 `prepareRequest()`（含 `agent/request` waterfall）成功之后、`llm.stream` 之前才提交 `user/message`。把准备逻辑放进 adapter 的 generate 内部会让准备失败的那条用户消息留在历史里，下一回合 adapter 的差分游标看到两条未投递的真实用户消息而报 `CODEX_SESSION_HISTORY_MISMATCH: unexpected-tail`（已复现）；挂在 `agent/request` 上则与原行为一致，准备失败不提交输入，修正运行条件后可重试原会话。

## 修复方案

阶段 A（本次）：解除依赖、恢复构建，并把工具过滤的执行点落到既定位置。

1. 新建 `packages/codex-cli/src/tool-selection.ts`：从原会话记录找回 `ToolSelectionSchema`、`ToolSelection`、`CliToolRow`/`CliToolControl`/`CliToolCatalog`、`ToolSourceId`/`CliTargetId`、`choiceEnabled` 的原始定义并本地化。`ToolSelectionSchema` 按 schemastery `transform` 的真实运行时语义（回调收到 inner 校验后的输出）声明为 `Schema<ToolSelection, ToolSelection>`，避免 Config 字段被推成可空。`choiceEnabled` 对 harness 侧在精确身份未命中时按名称回退，兼容 `profiles/kmh-mobile-assistant` 中已持久化的旧来源 id。
2. `tool-policy.ts`：删除 `cliTools` 服务注册、`tools/change → cli-tools/change` 转发、`agent/request-tools` 处理器、`observeNative`，以及对 `inventory/registeredInventory/presentation` 的调用；新增 `agent/request` waterfall 逐回合准备（`untilPrepared` 复用原逻辑，按回合号冻结），`forStream()` 返回完整 `PreparedPolicy`；`harnessRows`/`snapshotInventory` 改用 `tools.schemas()`；guard 改用 `tools.get()` 比对参数指纹。
3. `adapter.ts`：`drive()` 按 `forStream().names` 过滤 `options.tools` 后再交给 Codex；辅助请求（无会话或未准备）原样传递。`turn.ts` 去掉 `observeNative` 调用。
4. `session-store.ts`：`inventoryEntry` 的 `sourceLabel`、`sdk` 改为可选并剔除 undefined，旧记录仍可解析，新快照来自公开 `schemas()` 投影。
5. client：删除 `ToolRecords.tsx` 及其挂载、文案与测试；LiveBall 走自有 `/api/codex-cli/live` 路由，保留。`package.json` 删 `dsh-cli-tools`、`dsh-client-ui-chat`（无引用），保留 ui-renderer（提供 `ctx.slots` 类型）与 ui-conversation（声明 `conversation.composer.dock` 槽位）。
6. `bundles/dsh-web/cordis.patch.yml`、`profiles/kmh-mobile-assistant/{cordis.patch.yml,package.json}` 移除 cli-tools 条目；根 `pnpm install` 更新 lockfile。
7. 测试：harness 不再装载 cli-tools / selector 包；`tool-policy.test.mjs` 的 `cliTools.get().catalog()` 改为 `codexCli.toolPolicy.catalog()`，删除 `cli-tools/*` 事件断言、Selector 卸载重载用例，以及依赖补丁行为的 schema JSON 往返校验断言；其余"哪些 `kmh-` 工具到达真实 Codex 请求"的断言全部保留。
8. 文档：`packages/codex-cli/README.md` 工具选择与数据流改为当前实现；根 `README.md` 当前依赖状态与安装前提；`profiles/kmh-mobile-assistant/README.md`、`docs/spec/codex-cli-provider/tech-design.md` 同步。

后续阶段 B（未做，走 x-spec 立规格后实施）：独立的 `cli-tools-selector` 插件（KMH 自有包，优先适配 codex-cli）在 codex-cli 插件详情页可视化全量开关——数据来自 codex-cli 的公开通道（`toolPolicy.catalog()` 已能给出 harness/native 两列与控制类型，另需 `schemas()` 对比新增工具），可调项出 Switch、fixed/unverified 出只读标签与原因，写回经公开 settings 服务落 `config.toolSelection`。

依赖缺口与环境说明：`pnpm run setup` 在 Git 子模块布局下停在 DSH 根 `postinstall` 的 lefthook 安装（`core.worktree` 与 `extensions.worktreeConfig` 冲突），依赖已装齐；需在 `third_party/dsh` 内 `pnpm install --frozen-lockfile --ignore-scripts` 补齐安装状态后再 `pnpm --dir third_party/dsh run build`。本机 `~/.kmh/profiles/kmh-headless` 为既有目录，启动器拒绝建链，profile 依赖安装使用了临时 `KMH_HOME`。以上已写入根 README。

已知取舍：无插件来源标签（harness 行来源固定为 `harness`）；`toolSelection` 的 Config schema 含 transform，固定版 settings 浅复制后 JSON 往返不可再校验值（详情卡读写走自有路由，不依赖该往返）；会话时间线的工具记录卡与 `cli-tools/*` 事件随职责收缩移除。
