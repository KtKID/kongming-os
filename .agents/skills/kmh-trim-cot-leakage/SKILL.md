# 清理推理痕迹泄漏

推理痕迹泄漏（chain-of-thought leakage）是这样的文字：它的视角是写作会话而不是仓库——引用只有那个会话能看到的产物、叙述变更而不是状态、或与早已离开的评审者争论。修复从来不是单纯删除：当段落承载事实分句时，先把每个分句改写成在 HEAD 站得住的形式，再删掉它周围的记录；一个分句都不承载的段落（审计编号、控制流叙述）直接删除。**必需背景：** [kmh-prose-standard](../kmh-prose-standard/SKILL.md) 拥有本技能应用的完整命题规则；引用规则的历史理由见 [DSH 子模块的归档笔记](../../../third_party/dsh/.agents/notes/archived/process/2026-08-09-committed-artifact-citations.md)。本技能是指导，不是脚本。

## 唯一的检验

对每个可疑段落问：**HEAD 处的读者，在看不到任何会话记录、PR 线程或未提交草稿的情况下，能否解析每个引用并验证每个论断？** 若不能，从仓库的视角改写存活的事实并删掉其余；若能，它就不是泄漏，无论听起来多历史——但可解析性只过本技能这一关：在现状表面（README、文档、JSDoc）上，可解析的变更故事仍然是变更叙述，第 3 类会把它送回它的合规归宿。

## 分类

1. **死设计会话引用** — `(decision 7)`、`(audit C2)`、`design §4.7`、`plan §1.4`、阶段标签（`T4`、`W3`、`P-I`）、"设计台账"、"(B 裁决)"。若决策有已提交的归属物，按名称和路径引用它；否则删除引用，并把它的事实分句改写成自立形式。
2. **栈与 PR 视角** — "本栈后面某个 PR"、"这个 PR 添加"、"上一个 commit"。陈述已交付的机制或扩展点；推迟的工作移到 `TODO` 标记或 issue 引用。
3. **变更叙述与版本戳** — "used to"、"no longer"（不再）、"旧的 X"，以及索引性戳记（"v1"、"这次裁剪"、"今天"、"现在"对比过去状态）。陈述当前行为；修复后的回归写成现在时反事实（"没有 X，就会发生 Y"），绝不写成仓库历史（"以前会 Y"）。
4. **评审编排** — "评审中被否决："、"评审者确认了"、草稿序数（"本笔记第 5 版"）、轮次归属。把存活的决策与理由保留为平实事实；删掉谁在何时说了它。
5. **面向评审者的辩解** — "这个 cast 是安全的——它只是……"、"这是对的，因为……"。为自身正确性辩护的注释是在对评审者说话，不是对维护者。陈述使代码安全的那个不变量；代码已展示时删掉注释。
6. **复述与推导记录** — 控制流叙述（"先做 X，再做 Y"）、测试走查、显然分支的证明。删除；只保留非显然的契约或不变量。
7. **含糊话与计划残留** — "目前大概没问题"、"应该够了"、没有任何标记的推迟。升级为 `TODO`/`FIXME`，或改写成实际的界限；删掉含糊话。
8. **写作语言混杂** — 中文为主的正文或注释里残留的未翻译工作语碎片（英文草稿语、`---- 私有 ----` 式会话分隔符），或英文正文里混入的中文残留（"端"、"设计稿"）。统一语言或删除。

## 什么不是泄漏

无辅助的引用清理会两头失败：删掉持久的引用，留下死的。按原文应用这些保留规则；[示例](references/examples.md)逐条校准：

- **Issue 引用** — `#1470`、`TODO(name):`、"issue #N 拥有后续工作"在 HEAD 可解析；任何表面都保留，包括 README。不要把它们搬进笔记。
- **笔记与复盘中引用已合并的 PR 和 issue** — 按所属文档的变更叙述归置规则，是允许的证据形式。
- **抑制理由** — lint 抑制注释的理由（`xxx-disable … -- 理由`）、覆盖率忽略说明、空 catch 的解释是必需文字；理由失实就修正理由，绝不删除。
- **现在时反事实的回归钉** — "没有 X，Y 就会发生"、"天真的 X 会……"。
- **实测界限** — "(实测: 512 层 ≈ 0.15s)" 为常量定标；"实测"这个证据词是承重的。
- **运行时的旧/新状态** — "旧连接先排空，新连接才开始接受"是运行时生命周期，不是变更历史。
- **笔记变更叙述小节里的历史阶段名** — "第一版交付了 X"在那里对现状安全；索引性戳记（"这次裁剪"）在任何地方都禁止。
- **设计上在仓库外解析的外部引用** — 标准分节（RFC 9110 §10.1.5）、Figma frame 名称；§ 禁令针对未提交的内部草稿，不针对外部标准或拥有自己 § 编号的已提交文档。
- **项目语气与体裁形式** — 作为项目语气的"我们"；笔记的"考虑过的备选"小节。

## 工作流

1. 范围与排除按 [kmh-prose-standard](../kmh-prose-standard/SKILL.md)：要求显式范围；绝不碰 `third_party/`（子模块文字遵循其自身规则）或归档笔记目录。记录的夹具与快照是派生物，不是文字目标：只有授权的行为改动需要新证据时，才改拥有它的源或场景并重新生成。
2. 先只读审计：运行[召回模式库](references/recall-batteries.md)（带 `--hidden` 以覆盖 `.agents/`），每个探针先用一个已知阳性和一个近似阴性校准，再信任其输出，然后对每个命中做语义判断。模式库是探针，不是定义——历次清理的人工复查都能发现它漏掉的案例，所以还要在手里没有模式的情况下通读范围内最密集的文字（模块 JSDoc、README、设计笔记）。
3. 按表面先修拥有者：生成目录 → 追溯每个消费者，先修源 JSDoc 或生成模板，再重新生成全部派生物；模型或用户可见文案 → 经由 [kmh-prose-standard](../kmh-prose-standard/SKILL.md) 处理，只在拥有对应行为证据时修改，否则保持原样并报告推迟；涉及子模块的双语配对文件 → 遵循子模块的配对规则（参照 [dsh-doc](../../../third_party/dsh/.agents/skills/dsh-doc/SKILL.md)），不在 Kongming 层单侧修改。
4. 删除任何东西之前，枚举段落的命题（prose-standard），并核对[示例](references/examples.md)中的"矫枉过正的陷阱"一节：把义务翻转为认可、把假想提升为已交付功能、删掉真事实、丢掉证据来源的精简。
5. 验证：重跑模式库，期望只剩合规保留、本技能自己的目录和拥有笔记的引用证据；确认每个残留引用在 HEAD 可解析；为触及的表面运行相应检查——Kongming 层为配置或启动变更 `pnpm test`、脚本改动 `pnpm lint`，子模块文件遵循子模块的检查。
