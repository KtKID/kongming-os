# DeepSeek Harness 客户端 UI/UX

这项技能提供指导，不是一份完整的检查清单。它覆盖 lint、typecheck 和 i18n 门禁无法判断的设计决策：反馈出现的位置、需要复用的内容，以及界面在窗口边缘和不同平台上的行为。文案质量遵循 [dsh-prose-standard](../../../third_party/dsh/.agents/skills/dsh-prose-standard/SKILL.md)；本地化归属遵循 [locale-owned copy decision](../../../third_party/dsh/.agents/notes/implemented/architecture/2026-08-23-locale-owned-client-ui-copy.md)；样式归属和 token 规则位于 [docs/web-styling.md](../../../third_party/dsh/docs/web-styling.md) 与 [ui-primitives 组件目录](../../../third_party/dsh/packages/client/ui-primitives/README.md#component-catalog) 中——本技能在这些规则之上补充设计判断，不重复复制这些规则。

## 视觉基础

- **使用现有的颜色、圆角和间距 token。** 引入字面量值前，先在目标页面及其最近的成熟同类页面中搜索已经使用的 token 或值（Plugins 页面通常是完整页面界面的参考），然后采用已有值。整套界面处理同样遵循此原则——Toast、菜单、消息内资源预览、侧边栏标签布局、颜色、留白规则和页面内边距：只要已有成熟组件或规则，就复用它，避免创建并行方案。
- **在浅色和深色模式下验证每一种颜色。** 颜色与背景的组合在两种主题下都必须保持可读，然后才能发布。变暗色调是常见反例：它们适合装饰性界面，但用于文本时经常在某一种主题下低于可读性阈值——未经两种主题验证，不要将变暗颜色用于文本。
- **新增或修改的功能 CSS 中，字体粗细最高使用 500。** 强调内容使用字号或墨色区分，避免使用 600 及以上的字重。ui-theme 负责的 Markdown 排版 token 属于既定例外。
- **已有对应角色时，从主题排版变量中选择字号，否则沿用页面现有字号层级。** 同类内容使用相同字号；不要为单个元素创造专属字号，并尽量减少页面上的字号种类（13px 是既定的行/详情字号）。页面本身缺少参考时，借用最相似现有页面或元素的字号与间距比例。
- **图标、文本和相邻元素保持比例与对齐。** 每个元素都要沿着明确的轴线与同类元素对齐（基线、垂直中心或共享边缘），图标尺寸要与旁边文本保持比例；不要发布没有对齐参照或明显压过相邻元素的界面元素。

## 优先复用

- **创建新组件前，先扩展现有组件、容器或交互。** 能融入现有界面的新能力（例如增加菜单项、为已有 primitive 增加 prop）优于在旁边堆叠平行元素。
- **图标来自现有图标库。** 选择语义最接近的现有图标；新增图标需要设计师审批后才能落地——评审新增图标的 PR 时，建议请求设计师评审。
- **右侧栏内容要在现有侧边栏中注册 slot。** 每个侧边栏标签都要声明与其含义匹配的标签图标。
- **含义不明显的纯图标操作需要 Tooltip。** 指针必须停留或选中才能查看的信息内容使用 HoverCard。优先使用这些共享 primitive，避免使用临时的 title 属性。

## 反馈界面

根据消息相对于产生它的界面的生命周期来选择反馈界面：

- **短暂的操作结果使用全局 Toast primitive。** 不使用原位提示；Toast 的状态和渲染要放在生命周期长于报告界面的宿主中（例如 `shell.overlay` 条目，RowActionToast 采用的方式）。由面板自身渲染的 Toast 会随面板卸载。删除操作可能关闭发起请求的面板或标签页；只有由界面之外的宿主持有的 Toast 才能在关闭后继续存在。报告成功和失败，省略仍在进行中的状态。
- **失败操作保留数据可见性。** 删除失败时保留对应行，由 Toast 宣布失败。保留瞬时操作的原有内容，使用提示表达错误。
- **原位提示用于与界面自身绑定的状态。** 例如带 Retry 操作的查询失败，以及由表单自身负责的字段校验。已填充内容的面板在保留内容旁显示紧凑提示；只有空面板才居中显示完整错误状态。
- **错误文案使用简洁的日常语言。** 除非为了调试必须暴露错误码，否则不使用内部术语或技术名词。优先使用一个清晰句子；两句话可以解释清楚的内容不要扩展成段落。中文提示最多使用两句话，并省略末尾句号（。）。提示不能破坏现有布局——预留空间或采用覆盖方式；保持相邻元素位置稳定。

## 加载状态

- 列表使用对应的 skeleton；其他页面级加载统一在中心显示裸 spinner。不要把 spinner 放在页面角落。
- 每个页面或组件统一使用一种加载处理方式，避免并发区域各自闪现不同样式。
- 只有上下文确实需要时才显示加载文案（窄侧边栏几乎从不需要）。

## 覆盖层与菜单

合并前，每个菜单、弹出层和 Tooltip 都必须验证以下三点：

- **可关闭：** 点击外部区域可以关闭；具备焦点能力时，按 Escape 也可以关闭。
- **适应视口：** 界面会滑动或翻转，以保持在窗口内部并保留边缘间距；只翻转到确实有足够空间的一侧，避免两侧都放不下时反复振荡。
- **不被裁剪：** 脱离 `overflow` 祖先和包含块的裁剪范围（必要时 portal 到 body），并确保不会被相邻元素遮挡。

滚动条保持在容器内部：使用共享滚动条样式，避免组件专属选择器；验证滚动条既不会溢出容器，也不会被圆角或边缘裁剪——保留少量内缩间距，避免滚动条紧贴容器边缘。

## 平台窗口适配

- 任何新增的标题栏元素或完整页面都必须考虑 macOS 和 Windows 的窗口装饰。macOS 的标题栏留白使用 `--dsh-frame-top-clearance`，Menu、Modal 和覆盖层 primitive 将它作为顶部安全边距使用——不要为了修复单个页面而修改全局变量。在页面自己的内边距上增加作用域限定的 `[data-platform='darwin']` 覆盖，并在页面样式规范中断言该覆盖。
- 评审时说明预期的总偏移量（留白 + 页面内边距），确保两个页面对“相同的顶部间距”达成一致，比较总和而非单个加数。

## 间距评审

- 检查每个变更区域的间隙：任何元素都不应在没有明确意图的情况下紧贴相邻元素，邻近图标和元素要保持该区域既有的间距。
- 平行元素优先保持对称；缺乏解释的单独间隙或偏移通常意味着遗漏了共享值。

## 设计评审升级

- 大量修改 UI 的 PR，以及任何用户能够明显感知到的 UI 或交互变更，都必须经过设计师或产品评审。当没有相应角色的审批人时，建议向设计/产品评审人员请求评审（截至 2026-09 的名单：yx zhang、yifffan、zhangziya、gaokaige；成员变化时在此更新名单）。
