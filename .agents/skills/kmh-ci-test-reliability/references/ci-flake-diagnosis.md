# CI 偶发失败（flake）诊断

仅在任务是调查既有的概率性测试或 CI 失败时使用本流程。保持请求赋予的读写范围：诊断不授权修复、重跑工作流或修改 CI 配置。

## 冻结证据

记录仓库、执行入口（`pnpm test`、pre-push 钩子或 CI 作业）、作业、commit SHA、执行环境标签、时间戳、精确的失败测试或命令，以及第一条稳定的失败签名。基础设施消息与测试输出分开保存。

对比多个失败与通过的运行。优先使用同一 SHA 的运行；做不到时，核对被比较的 commit 之间相关测试与 CI 配置完全一致。一次通过的重跑证明不了基础设施故障，一次 timeout 也证明不了产品竞争。

用执行入口的日志与元数据判断失败是否在同一个主机或资源命名空间上重叠。保存佐证运行的链接，而不是粘贴大段日志。

## 给失败分类

从记录到的证据分类，而不是从最终的修法分类：

- **主机资源冲突：** 同一端口、套接字、数据库、可预测路径、缓存或外部命名空间被独立进程或作业获取。
- **生命周期不完整：** teardown 在子进程、worker、流、服务器或回调达到静止之前返回；后续输出或修改出现在另一个测试里。
- **进程全局污染：** 结果取决于测试顺序，或泄漏的 `process.env`、`cwd`、fake timers、全局对象、mock、locale 或模块状态。
- **负载敏感的同步：** sleep、轮询间隔或假想的事件循环轮次替代了可观察的就绪或完成。
- **平台或入口路径不匹配：** 失败稳定跟随某个操作系统、shell、文件系统规则、源码/构建模式或可执行入口。时间戳精度、环境变量名大小写、句柄释放时机与权限语义在 Windows 与 POSIX 主机上都不同，所以 macOS 上通过的用例说明不了 Windows 车道的行为。
- **产品并发缺陷：** 测试控制自己的资源，以显式重叠确定地复现，并暴露已交付行为中的竞争。
- **外部提供方瞬时故障：** 失败由真实 API 或网络边界拥有，并与该边界的文档化重试策略相符。
- **执行环境基础设施：** checkout、依赖下载、磁盘、主机进程或执行器服务独立于测试命令失败。归入此类需要执行器的直接证据。执行器池不暴露主机指标时，如实说明，并从日志实际携带的内容分类：同一签名在同一个池上跨不相关分支重复出现，即共享主机争用的证据，即使无法检查该主机。

证据支持多于一条独立事实时，逐条报告。不要把 timeout、信号、退出码与断言坍缩成单一推断结果。

## 复现最小相关拓扑

从拥有该失败的测试文件或聚焦测试名开始。只把并发提高到第一个复现签名的拓扑：

1. 单个测试文件单独运行；
2. 提高文件或用例的并发；
3. 多个独立的测试进程；
4. 完整仓库入口（`pnpm test`，含 `pretest` 构建与当前 `--test-concurrency` 配置）；
5. 共享被怀疑主机资源的多个作业或执行入口。

对齐当前测试配置、环境开关、源码/构建模式（`packages/kmh-echo/lib` 是否最新）与平台。不要为了制造另一种失败而调低产品 timeout 或添加随机负载。

签名所属的平台是可用主机无法运行的，阶梯停在最后一个可达的梯级。记录该限制，而不是用另一平台上的通过运行替代；此后把 CI 当作复现手段，每次只改一个被怀疑的拥有者，让结果保持可归因。

怀疑竞争时，用争夺点上的 barrier 替代概率性时序。怀疑主机冲突时，证明同一标识被同时获取，或证明原子唯一分配消除了冲突。

## 在拥有者处修复

获得修复授权时，修复分配资源、发布就绪、修改全局状态或拥有 teardown 的那个组件。不要把失败藏进快照归一化、重试包装、更宽的 timeout、全局串行化设置或更弱的断言。

保持稳定的 fixture 数据与真实资源分配分离。录制的 URL 可以保持稳定，同时由 fixture 把它的传输映射到操作系统分配的端口；稳定的期望路径可以继续作为断言，而不必变成共享的可写目录。

## 结束调查

证据完整当：

- 原始签名有了有依据的分类；
- 最小相关拓扑复现了它，或外部证据已足够且复现限制被明确记录；
- 已授权的修复在阴性对照或修复前状态下失败，在同一拓扑下修复后通过；
- 资源拥有者要求的并发进程、恢复或静止 teardown 证明全部通过；
- 其余检查按观测状态报告为通过、等待、跳过或失败。

不要跑到测试恰好通过就宣布结果稳定。选定证据足以建立结论时停下，或报告阻塞分类的缺失事实。
