# KMH 测试的 CI 稳定性

让测试在仓库真实的执行拓扑下保持正确，而不是只在安静的开发机上单独运行时正确。本技能负责隔离与可靠性判断；它不替代 push 命令的选择，也不改写子模块的测试规则。

## 先读所属规则

- 根 [AGENTS.md](../../../AGENTS.md) 规定验证入口：启动与配置变更运行 `pnpm test`，脚本修改运行 `pnpm lint`。Kongming 目前没有独立的测试分层政策文档；证据类型的选择以该文件的验证要求与 [kmh-pre-push-checks](../kmh-pre-push-checks/SKILL.md) 的改动面表为准。
- 阅读当前测试入口的实际拓扑：`package.json` 的 `test` 脚本为 `node --test --test-concurrency=1 tests/runtime/*.test.mjs`，`pretest` 先执行 `pnpm build:kmh` 构建自有插件；`pre-push` 钩子运行同一启动测试。并发度、文件清单或参数变化会改变下文的拓扑假设。
- `third_party/dsh` 子模块内的测试遵循子模块自己的规则与检查；深入 DSH 时参照子模块原技能 [dsh-ci-test-reliability](../../../third_party/dsh/.agents/skills/dsh-ci-test-reliability/SKILL.md)，本技能不重复其内容。
- 测试设计可靠之后，用 [kmh-pre-push-checks](../kmh-pre-push-checks/SKILL.md) 选择 push 前的验证命令。

## 建模执行拓扑

除非当前配置证明相反，假设以下层级可能重叠：

1. 同一测试文件内的用例（`node:test` 默认按定义顺序运行）。
2. `tests/runtime/` 下的不同文件——当前由 `--test-concurrency=1` 串行，但这是运行参数，不是隔离保证；提高并发、单独运行某个文件或改用其他参数时，这些假设全部失效。
3. 同一条 `pnpm test` 内的 `pretest` 构建进程与测试进程先后运行。
4. pre-push 钩子、开发者手动运行与 CI 作业等不同入口共享同一台主机。

进程隔离不隔离主机端口、可预测的文件系统路径、外部服务、数据库、套接字或继承的子进程；Kongming 还有仓库内共享文件——测试会改写 `profiles/*/cordis.patch.yml` 与 `launch.config.json`。对每个获取的资源，识别它的拥有者、原子分配机制、可观察的就绪信号、已登记的清理，以及静止（quiescence）完成信号。

不要因为一个 fixture 缺少隔离就把整个套件串行化。先收窄独占范围或改掉资源分配方式。串行块保护不了主机资源不被另一个文件、进程或执行入口占用。

## 原子分配资源

使用资源拥有者的分配器，而不是先检查可用性、之后再占住。

- 网络 fixture 用 `listen(0)` 绑定回环地址，在服务器报告监听之后才读取分配到的地址。绝不扫描空闲端口之后再绑定。
- 用 `mkdtemp` 为每个测试创建私有的临时根目录；不要获取可预测的共享路径。现有测试即为范例：以独立 `mkdtemp` 目录作为 `KMH_HOME`，不共享 `.kmh` 或仓库内的运行目录。
- 共享的数据库、套接字、会话与输出位置按测试给唯一命名空间。
- 某个路径必须不存在时，使用独占创建。
- 稳定的录制标识与临时的传输地址分开保存。在 fixture 内部做翻译，而不是强迫真实资源使用录制值。

仅作为解析器输入或期望值使用的字面路径与 URL 不是被获取的资源。不要因为它们看起来写死而改写它们。

## 收敛进程全局状态

把 `process.env`、`cwd`、fake timers、locale 与时区、模块 mock、注册表、console 钩子、`globalThis` 和全局 `fetch` 拦截当作独占的可变资源。

优先使用注入的依赖或实例本地的适配器。现有测试直接向 `spawnSync` 传入独立 env（含 `KMH_HOME`）而不是修改 `process.env`，就是注入优先的直接做法。确实需要修改时：

- 记录原值是缺失还是存在；
- 恢复到那个精确状态；
- 立即登记恢复；
- 用 `try/finally` 包住最小的修改作用域；
- 本地 `finally` 之前可能失败时，保留用例级恢复钩子（`t.after`）兜底；
- 只拦截 fixture 拥有的最窄的精确请求或调用。

改写仓库共享文件（如 `profiles/kmh-web/cordis.patch.yml`）时同样如此：修改前读取原内容，立即在 `t.after` 中恢复精确原文，把改写放在最小作用域内——现有 `tests/runtime/launcher.test.mjs` 即此模式。

## 尊重平台归属语义

同一套件可能在不同操作系统与文件系统上运行，操作系统拥有的值不一定按测试写入的方式读回。

- 写回一个值是安全的，仅当断言容忍写回失败。恢复文件的 `mtime` 以证明指纹反正会失效，这在任何平台都成立；恢复它以证明记录仍然有效，则假设无损往返，而 NTFS 的 100 纳秒刻度给不了亚毫秒精度。断言依赖恢复结果时，从一次新读取取期望值，而不是从记忆值。
- Windows 不区分环境变量名的大小写，fixture 同时播种 `http_proxy` 与 `HTTP_PROXY` 两个键时，在那里只会得到一个条目。
- Windows 异步释放文件句柄，在 POSIX 主机上立即完成的改名或删除，在那里需要按实际观测到的争用设定有界重试。
- Windows 没有 POSIX 权限与信号语义。依赖它们的用例要写明理由的显式平台跳过，而不是在所有平台弱化断言。

优先使用在每个平台都成立的观察。用例确实无法做到时，在该平台上显式排除它。macOS 上通过的用例证明不了对应平台车道上的行为。

## 按执行环境预算 timeout

用例上声明的 timeout 覆盖运行器的默认值，而不是与其叠加：低于整体预算的值削减了执行入口已经给出的宽限；同一字面值在默认更小的机器上又读作放宽。受进程创建主导的测试对齐整体预算；设得更紧的值必须携带更紧的理由。

同步提高清理钩子的预算。setup 与 teardown 承受同样的争用，只提高用例预算会把争用失败挪进清理钩子。

timeout 本身是被测对象时，外层等待必须远大于被测 timeout。证明一个 20 ms 的截止时间会触发的用例，不能与运行器自身的等待竞争，否则负载决定哪个截止时间先报告。

## 以状态同步

固定 sleep 不是 setup 已完成或清理已停止的证据。

- 等待显式的就绪事件、握手、状态转换、自己持有的 promise 或外部可观察条件。
- 用 deferred promise 或 barrier 把竞争放到确定的位置，并证明相关操作确实重叠。
- timeout 只用来给等待设上界，绝不是让断言成立的前提条件。
- 不断言依赖调度顺序的排序，除非该排序本身就是被测的产品行为。
- 时间本身是被测对象时，注入或伪造时钟，并始终恢复真实 timer。

## 清理到静止

获取资源之后立即登记清理，让断言失败同样释放资源。清理要停止新的回调或请求、摘除监听器、恢复全局钩子、终止自己拥有的工作，并等待子进程退出、服务器关闭、worker 终止或等价的完成信号。

调用 `abort()`、`close()` 或 `kill()` 而不等待自己拥有的完成信号，是不完整的 teardown。现有 `kmh-echo` 测试在删除目录前 `await fiber.dispose()`，就是在等待静止信号。可能晚点完成时，证明清理会阻止它污染另一个测试。

## 证明目标回归

- 实际可行时，先观察普通回归在修复前失败。
- 新增静态或语料守护时，临时引入被拒绝的用例，观察预期失败发生。
- 竞争类问题用 barrier 证明重叠；单纯重复执行不是竞争测试。
- 端口、套接字、共享路径、子进程或其他主机资源相关时，跨进程隔离本身就是修复的一部分，就要以独立测试进程并发运行来证明。
- fixture 以自己的截止时间 spawn 时，先断言没有信号或 timeout 提前终结子进程，再断言退出状态，否则被杀的子进程会以 timeout 而非状态不符报告出来。
- 验证外部状态、事件、文件、日志、退出或清理结果，而不是相信组件的自我报告。

压力运行是确定性回归的补充，不能替代它。

## 拒绝掩盖 flake 的修复

对本地确定可复现的失败，不要把下列手段当作根因修复来提交：

- 未识别等待目标就加大 timeout；
- 添加重试；
- 把所有文件改为串行；
- 吞掉错误或未处理的 rejection；
- 弱化断言；
- 把不稳定行为归一化掉；
- 在清理或断言前加 sleep。

对有文档依据的瞬时外部提供方测试，重试仍然有效。把这个例外留在真实外部边界上。

恢复预算不是掩盖。把套件恢复到执行入口本已给出的预算，或把有界重试设为执行环境上实际测得的争用规模，同时指名等待中的工作——这两者都不是在未审视的等待周围发明余量。

## 诊断既有 flake

对既有的概率性 CI 失败，按 [CI 偶发失败诊断流程](references/ci-flake-diagnosis.md)执行。仅诊断的请求保持只读：报告原因与证据，除非用户同时要求修复。

## 验证与报告

为受影响的行为运行最小的聚焦回归。测试导入的是构建产物（`packages/kmh-echo/lib`），直接运行单个文件前先确认 `pnpm build:kmh` 已执行（`pnpm test` 的 `pretest` 已包含）。

仅当改动自己拥有该风险时，才追加拓扑对应的证据：

- 全局修改需要恢复证据；
- 生命周期或子进程工作需要静止 teardown 证据；
- 端口、套接字或共享路径需要独立进程并发的证据；
- 新增守护需要阴性对照。

push 前使用 [kmh-pre-push-checks](../kmh-pre-push-checks/SKILL.md)。报告精确的命令与观测结果；不得把重试、跳过的测试或尚未结束的 CI 描述为通过。
