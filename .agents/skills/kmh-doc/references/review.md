# 评审标准

## 概述

评审文档看读者能否完成目标，而不是模板标题是否齐全。对照代码与测试核实文字，保留精确契约，让包 README 对使用者有用，同时向维护者暴露足够的实现细节。

## 新人测试

无仓库背景的工程师应在三到五个链接页面内回答：产品或功能做什么、如何安全地运行或使用、状态存在哪里、哪个组件拥有它、如何失败、去哪里改。读者必须翻源码才能发现公开流程时，补回缺失的解释；读者被迫吸收无关内部细节时，把这些细节下移。

## 证据审查

逐条对照最强归属核查实质性论断：包清单（`package.json`）负责名字与入口，导出类型与注释负责 API 契约，运行时代码负责行为，测试负责被行使的失败路径，归属文档负责取舍理由。任何旧 README、讨论或报告都不强于当前代码与测试。

对每条操作类论断——命令、配置片段、默认值、报错、平台差异——证据是运行它，不是读到它。页面对其陈述行为之前，先对当前 checkout 执行确切的命令或挂载确切的配置；只引用观察到的输出、警告与失败。依赖不可用密钥或网络的论断，指名验证归属而不是断言行为。

评审安装或接入指引前先分类包形态：`src/index.ts` 导出 `apply` 或默认服务的是插件（`cordis.patch.yml` 挂载行）；纯模块 API 是库（作为依赖被引用，无挂载路径）；`bundles/` 下的目录是 bundle 包（由 profile 声明选择）。拒绝为别的形态写的指引。

只在论断帮助目标读者行动、推理或避免误用时保留它。理由、历史、测试走查、重复目录与无关包细节移交给各自的归属。

## 包 README 审查

要求以下各项，但不强套统一的内部标题集：

- frontmatter 只含 `description`，一两句具体描述并含可检索的领域词；
- 概述三到五句，说明该包对其读者"能做什么"，后接目录；
- 受控表述：明确主语、稳定术语、直接动词、指令与条件分离、模态不变；
- 何时选择或避免该包；
- 存在最短安全路径时给出它——插件是 `cordis.patch.yml` 最小挂载，bundle 是 profile 声明方式，库是消费者入口；不给不适用的形态写接入指引；
- 配置键表：字段、默认值、一行含义；穷举字段链接权威归属而非复制；
- 验证章节：在 Kongming 根目录实际运行过的命令与成败观察方式；
- 归属链接：所属 `docs/` 页面（如 [Web 插件索引](../../../../docs/kmh/plugin-index.md)）、相邻包与上游实现，各配一句增量说明；
- 消费者相关的可观察行为、失败、持久性、安全与性能限制；
- 开发者归属与数据、生命周期设计，加代码链接；插件逐个覆盖脚本用途、实现机制与关键函数，按[脚本与关键函数说明](../SKILL.md#插件的脚本与关键函数说明)核对当前文件与调用关系；
- 末尾非权威开发备注，作为半成品想法与待定方向的唯一归宿。

用户向章节描述读者可见的能力、配置和操作。内部函数、事件流与数据流放在开发者章节，按实际工作过程解释，并链接其源码归属。评审时核对新人能否读懂每个脚本解决什么问题、怎样完成工作，以及关键函数之间如何配合。

## 参考示例

[packages/kmh-echo/README.md](../../../../packages/kmh-echo/README.md) 是 Kongming 包 README 的现行样例：概述讲清包做什么与生命周期表格，配置章节给出键、路径语义与 profile 挂载示例，验证章节列出实际运行的命令与测试覆盖。以其结构、证据标准为包 README 的基准。注意它是单一用途的小插件；复杂包按[包 README 模板](../templates/package-readme.md)补充归属链接与进一步探索。

## 验证

迭代时运行最小范围的聚焦检查，收尾时完成文档评审的固定动作：

```sh
git diff --check
```

Kongming 无专门的文档检查脚本，验证按 [SKILL.md 的验证节](../SKILL.md#验证) 执行：核对全部相对链接目标、实际运行所述命令；伴随启动或配置变更运行 `pnpm test`，脚本修改运行 `pnpm lint`。最后重读 diff 两遍：第一遍查事实完整性，第二遍查篇幅、导航与归属。
